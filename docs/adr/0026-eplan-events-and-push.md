## 背景与问题
M6 的上下文缓存（设计 4.7）需要知道 EPLAN 中的项目什么时候变了：工程师在界面中编辑、别的程序写入、项目被关闭或重新打开。现状：
- Bridge 只在一次调用期间发 `progress` 通知（`src/EplanMcp.Bridge.Core/Server/BridgeConnection.cs`），没有在调用之外主动发消息的通道；
- 插件只实现 `IEplAddIn`、`IEplAddInShadowCopy`，没有订阅任何 EPLAN 事件；
- EPLAN API 用 `Eplan.EplApi.ApplicationFramework.EventHandler` 按名称订阅事件（`SetEvent(名称)` 加 `NameEvent` 事件，XML 文档）；可用的事件名和参数要实测。S33 实测（api-notes A38）：数据变化的事件 `onDMObjectsAltered` 不带可读的范围，只能说明"项目中某些对象变了"，不知道是哪些页，被回滚的修改也会触发（提出时设想的 `Page.ConnectionDirty` 事件并不存在）；
- 没有事件时只能靠 TTL 和写前重新核对，缓存要么常常过期，要么要频繁重新提取。

这是 IPC 的变化，属于 L3，只能提议。

## 决策驱动因素
- EPLAN 主线程不能被拖慢；事件处理中漏出的异常会让 EPLAN 崩溃（S1，编码规范 5a）。
- **正确性不能依赖事件**：事件可能漏掉、没有覆盖全部修改、来自 Host 没连着的时候。
- 一个 Bridge 可能同时连着几个 Host（每个 MCP 客户端一个 Host 进程）。
- 不打乱现有的调用和响应。
- 通知内容来自 EPLAN 中的项目，按不可信的数据对待（[架构](../architecture/architecture.md) 8.5）。

## 备选方案
1. 不订阅事件，只靠 TTL 和写前核对。
2. Bridge 缓冲事件，Host 定期用 `events.since(序号)` 拉取。
3. **Bridge 在单独的订阅连接上推送带序号的通知，Host 断线重连后从序号续上，有缺口就整体标为待核对。**
4. 在现有的调用连接上与响应交错推送。

## 决策
选择方案 3（推送加序号，包含了方案 2 的续传能力）。

### 1. 订阅哪些事件
- 只订阅 S33 验证过的事件名，列在 Bridge 代码中的白名单里。S33（api-notes A38）验证过的：数据变化 `onDMObjectsAltered`（回滚的修改也触发，不带范围）、`onPreCommitTxn`、`onPreCloseUndo`；项目打开 `API.PreOpenProject`、`Eplan.EplApi.OnPostOpenProject`（带路径）；项目关闭 `onPreCloseProject`、`onPostCloseProject`。原候选 `Page.ConnectionDirty` 不存在。
- **事件名、参数和触发线程都要由 S33 实测核实，实现按实测的结果来做**；本 ADR 中关于具体事件的写法只是候选。
- S33 证明某个事件不稳定或代价过高时不订阅；一个也不能用时，握手不声明这项能力，Host 只用 TTL（第 6 条）。

### 2. 事件处理
- 在 `OnInitGui` 中注册，在 `OnExit` 中注销。
- 处理函数在 EPLAN 触发它的线程上只做最少的事：取出事件名和字符串参数，连同递增的序号放进有界队列；不调用其他 EPLAN API，不做 I/O，整个函数包在 `try/catch` 中，从不让异常漏出。
- 管道线程从队列中取出事件，在 250 毫秒的窗口内按（项目、页、种类）合并，再发给订阅者。

### 3. 协议
- Host 另开一个管道连接，握手后调用 `events.subscribe {fromSeq?}`；之后这个连接只承载 Bridge 发出的通知 `events.notify {epoch, seq, items: [{kind, project?, pages?, scope}]}`，不承载调用。
- `epoch` 是 Bridge 实例的标识（进程号、启动时间加随机值），Bridge 重启后改变；`seq` 单调递增。
- Bridge 保留最近 4,096 条；`fromSeq` 已经被挤出、`epoch` 变了、或者订阅者的发送队列满了，Bridge 发 `{gap: true}`，Host 把这个实例的全部缓存项标为待核对。
- 能力由握手的 `operations` 声明（`events.subscribe`）。旧的 Host 从不订阅，新的 Host 只在 Bridge 声明时订阅，所以**协议版本保持 1**，与 ADR-0010 增加 `outcome.get` 的做法相同。订阅连接与其他连接一样只允许当前用户（ADR-0008）。
- 一个 Bridge 最多 4 个订阅连接，超出的被拒绝；每个订阅者有自己的有界发送队列，慢的订阅者只会收到缺口标记，不会拖住别人。

### 4. 通知的含义
- `kind` 取页变化、连接变化、项目打开、项目关闭等；`onDMObjectsAltered` 不带范围（S33），发出 `{kind: "objects", scope: "unknown"}`，Host 把依赖连接的全部缓存项标为待核对（设计 4.7 的宽的待定范围）。
- 通知**只用来让缓存项失效或待核对**：从不作为写入的依据，从不触发写入或计划，从不原样转给 MCP 客户端当作指令。Host 可以据此给订阅了的 MCP 客户端发自己资源（计划、任务）的更新通知。
- Host 收到通知后只改缓存的状态，下一次使用时按设计 4.7 重新提取、比较页哈希。

### 5. 不依赖事件也正确
TTL 和写前重新核对（设计 4.7、4.8）始终保留。事件只减少过期的时间，不改变任何正确性的论证。计划的每一步仍在 Bridge 中重新规划、重算指纹。

### 6. 离线宿主
离线宿主没有界面编辑，不订阅事件，不声明这项能力。

## 后果
- **好的**：
  - 工程师在 EPLAN 中的修改能很快让缓存失效，上下文更少过期；
  - 序号和缺口标记让漏掉的事件变成"全部待核对"，而不是悄悄使用旧数据；
  - 调用连接不受影响，旧的 Host 和 Bridge 照常工作。
- **坏的或要付出的代价**：
  - Bridge 多了事件处理、队列和订阅连接，需要故障注入测试；
  - 事件处理运行在 EPLAN 的线程上，写错了会拖慢甚至弄崩 EPLAN，所以处理函数必须极简，并在 spike 中测量开销；
  - 没有参数的事件只能让大范围失效，效果有限。
- **后续行动**：
  - 先做 S33：可用的事件名、参数、触发线程、批量操作时的频率、`SafetyPoint` 回滚时是否触发、处理函数的开销，结论写进 api-notes；
  - [security.md](../standards/security.md) 增加"订阅连接上的洪泛或伪造通知"威胁及措施（编号按当时的最大值顺延）；架构 5.3、6.1 补充订阅连接；
  - 测试：Bridge.Core 的 Small/Medium（序号、合并、缺口、订阅者上限、慢订阅者、处理函数中的异常被吞掉）；Host 的 Medium（假 Bridge 推送后缓存状态变化、缺口时全部待核对、重连续传）；Large（在 EPLAN 中手工改一页，Host 的缓存项变为待核对）。

## 各方案利弊
### 方案 1：不订阅
- 优点：没有新机制，不碰 EPLAN 的线程。
- 缺点：只能靠 TTL，缓存要么过期、要么频繁重新提取。
### 方案 2：拉取
- 优点：不改变消息方向；实现简单。
- 缺点：要轮询，延迟取决于轮询间隔；MCP 资源订阅需要及时的变化。它的续传能力已包含在方案 3 中。
### 方案 4：在调用连接上交错推送
- 优点：不多开连接。
- 缺点：Host 的读取逻辑要区分响应和通知，长时间的调用期间通知会和进度、响应交错；现有的"一次调用一问一答"的假设被打破。
