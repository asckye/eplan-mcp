## 背景与问题
[M6 设计](../design/2026-10-21-m6-engineering-packs.md)的工程包会在工程师和公司之间交换（`.eplanpack`，ZIP）。包里有：
- EPLAN 原生文件：宏、基本项目、项目备份（`.zw1`、`.zw9` 是 7z 归档，api-notes A31）、表单、图框，由 EPLAN 解析，插入到目标项目中；
- EplanMcp 生成的 JSON：清单、知识文档、规则、工作流；
- 公司说明等文字，会进入模型的上下文。

一个包可能被篡改、损坏，或者本来就是恶意的：路径穿越覆盖数据目录之外的文件、解压炸弹、伪造的来源、夹带脚本、说明中的提示注入、引用外部文件而事后被替换。包是否可信、放在哪里、能引用什么，属于安全模型，是 L3。

并行的代码栈 PR #393–#396 已经实现清单 v0 和路径校验（`src/EplanMcp.Packs/PackPath.cs`：相对路径、`/` 分隔、按 SEC-19 拒绝 Windows 会改写或保留的名称、不区分大小写比较），本 ADR 在此基础上定规则。

## 决策驱动因素
- 包里不能有任何会被自动执行的东西：规则不编译表达式，工作流只引用封闭的操作目录（设计 4.8、4.11）。
- 已锁定的版本不能被悄悄改变：项目锁记的是摘要（设计 4.1.5）。
- 工程师决定信任谁；EPLAN 解析原生文件的代码我们无法加固，只能控制来源和打开的位置。
- 客户数据不进仓库（CLAUDE.md 第 4 条），也不应在不知情时随包流出。
- 0.x 没有代码签名证书（架构第 7 节），签名不能是使用的前提。

## 备选方案
1. 把包当作可信的，不校验。
2. **把包当作不可信的数据容器：安装前校验，签名可选。**
3. 要求每个包都签名。
4. 允许包携带脚本或插件，由工程师批准后执行。

## 决策
选择方案 2。

### 1. 只含数据
- 包中每个文件都必须列在 `pack.json` 的 `resources` 中，种类已知、扩展名在该种类的允许列表中：原生文件（`.ema`、`.emp`、`.zw9`、`.zw1`、表单、图框等，按 api-notes A31 登记的扩展名）、JSON、PNG、纯文本和 Markdown；SVG 只接受不含脚本、事件属性和外部引用的。
- 可执行或会被系统解释执行的类型一律拒绝，无论放在哪里、叫什么名字：`.dll`、`.exe`、`.ps1`、`.bat`、`.cmd`、`.vbs`、`.js`、`.cs`、`.msi`、`.lnk`、`.scr`、`.reg` 等，以及 EPLAN 脚本。
- EplanMcp 从不自动执行包中的任何内容：不运行脚本，不注册插件（ADR-0025 的插件不在包中），不执行 action；规则和工作流只由 Host 按封闭的格式解释。
- **修订（2026-10-21，项目负责人选择"允许，只存储不解析"）**：文档类资源（种类 `document`）另外接受 `.xlsx`、`.pdf`、`.docx`。EplanMcp 只保存它们、计算哈希，**从不打开或解析这些文件**，也不把它们当作物料对应表或规则；启用宏的 Office 文件（`.xlsm`、`.xltm`、`.docm`、`.dotm`、`.pptm`、`.potm`）无论放在哪里、登记为什么种类一律拒绝（`PACK_INVALID`）。解析 XLSX 物料对应表不在本修订之内，另行决定。

### 2. 容器校验（解开之前）
- 条目名：相对路径，`/` 分隔，没有 `..`、盘符、UNC、`:`（备用数据流）、保留设备名、结尾的点或空格，按 NFC 规范化后不区分大小写地唯一，总长不超过 240（与 v0 的 `PackPath` 相同）；拒绝符号链接条目。
- 上限（`config.json` 中只能调低）：压缩后 2 GB、解压后合计 8 GB、条目 20,000 个、单个文件 2 GB、单个条目的压缩比 200:1；不递归解开包中的归档，`.zw1`、`.zw9` 原样保存。
- 解到数据根目录下新建的临时目录，逐个核对大小和 SHA-256 与清单一致，没有多余的文件、没有缺少的文件，重算包摘要；全部通过后才移到 `packs\<包 ID>\<版本>\`。任何一项失败都整体拒绝（`PACK_INVALID`，列出原因），不部分安装。
- 同一包 ID 和版本已经安装而摘要不同时拒绝；版本从不覆盖。

### 3. 签名（可选）
- 签名是对包摘要的分离式 CMS 签名（`pack.sig`）。实现用微软的 `System.Security.Cryptography.Pkcs` 包（.NET 运行时仓库的一部分，不在共享框架中），引入时按新依赖记录（开发流程第 6 节）。
- 信任的发布者只能在 `config.json` 的 `packTrust.publishers` 中按证书指纹列出（SEC-02）；`packTrust.requireSignature` 默认 `false`，设为 `true` 时没有签名或发布者不受信任的包一律拒绝。
- 有签名而校验失败的包一律拒绝，不降级为"未签名"。

### 4. 安装要工程师确认
- 安装别人的 `.eplanpack` 要经审批渠道（ADR-0011）确认一次。确认的内容：包 ID、版本、发布者、签名状态、摘要、大小、原生文件的清单（宏、项目、备份的数量和名称）、能力要求、是否含有 `referenced` 资源。
- 从工程师自己放进 `imports\` 的材料构建开发包，不需要确认（设计 4.5.1）。
- 安装、构建、删除、项目锁的变化写审计（`pack_change`，记摘要）。

### 5. 放在哪里
- 已安装的包在 `<数据根目录>\packs\`，设为只读，每次使用前按清单核对哈希；开发包在 `packs-dev\`。从不放进 EPLAN 的主数据目录或安装目录：EPLAN 和其他工具会改写那里的文件，无法保证不可变。
- `macro.insert` 和 `module.insert` 在 `$(MD_MACROS)` 之外增加一个根目录：`packs\`。路径按 SEC-19 校验（相对路径，路径上没有链接和联接点）；Bridge 在打开宏之前再按清单核对一次文件的 SHA-256。
- 参考项目和基本项目只在 scratch 中还原或新建后由 EPLAN 打开，从不打开包中或原位置的项目；还原只到新建的空目录（EPLAN 会覆盖已有的项目，A31）。

### 6. 企业资源的引用
- 默认把企业资源（例如网络共享上的公司宏库）复制进包，记下哈希。
- 只有 `config.json` 的 `packSources` 中列出的根目录（可以是 UNC），才允许 `referenced` 方式就地引用；只读，从不写入；每次使用前核对哈希，不一致时该资源不可用（`status` 说明原因），从不悄悄改用新的内容。
- 清单只记录相对于输入或根目录名的路径，从不记录本机的绝对路径（v0 已如此）。

### 7. 包中的文字是数据
说明、资源名、规则的消息等只放在结果的数据字段中，剥除控制字符、限制长度（[架构](../architecture/architecture.md) 8.5）；从不因此生成规则或计划。规则消息中的占位符只填入数据。

## 后果
- **好的**：
  - 包可以放心地在人之间交换：最坏的情况是被拒绝安装，或安装后被标为不可用；
  - 锁定的版本不会被悄悄改变；
  - 公司可以签名，工程师可以要求只装签名的包；
  - 企业资源可以就地引用，但被替换时会被发现。
- **坏的或要付出的代价**：
  - 安装要多一次确认，大包的校验要花时间；
  - 恶意的原生文件仍可能触发 EPLAN 自身的缺陷，这里只能控制来源和打开的位置；
  - 签名的密钥和证书管理由公司自己负责。
- **后续行动**：
  - [security.md](../standards/security.md) 增加"恶意或损坏的工程包"和"就地引用的企业资源被替换"两条威胁及措施（编号按当时的最大值顺延，现为 T31、SEC-34）；
  - M3b 设计 Q3 和工具规格中的宏路径规则加上 `packs\`；
  - `doctor` 显示 `packTrust`、`packSources` 和包占用的空间；
  - 测试（Small）：路径穿越、保留名、大小写重名、符号链接条目、超限、压缩比、多余或缺少的文件、哈希不符、签名不符、可执行类型、含脚本的 SVG；Medium：安装确认被拒绝时不留下任何文件。

## 各方案利弊
### 方案 1：当作可信的
- 优点：简单。
- 缺点：一个被篡改的包就能覆盖任意文件或夹带脚本；违反 ADR-0005 "安全不靠模型和客户端的自觉"。
### 方案 3：强制签名
- 优点：来源明确。
- 缺点：0.x 没有证书，公司也未必有；工程师之间交换开发中的包会被挡住。保留为 `requireSignature: true` 的选项。
### 方案 4：允许脚本或插件
- 优点：包能带算法。
- 缺点：等于让包执行任意代码；算法需求由 ADR-0025 的插件单独满足，插件不随包分发。
