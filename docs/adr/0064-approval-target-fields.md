## 背景与问题

ADR-0035 规定破坏性问题的批准分两步：先点写着具体动作的按钮（“删除页…”），再在确认面板里输入确认值（例如页号），并要求“确认值只取 Host 问题里的结构化字段”。同一份 ADR 的第 5 条又规定审批协议和问题字段不变。

2026-11-20 落实时发现两条对不上：审批问题（`ApprovalAskParams`）里与目标有关的只有工具名、项目和变更清单。变更清单是给人读的文字，内容来自项目数据，不能当确认值。所以现在的实现是：

- 确认值用**项目名称**；
- 按钮文字是“执行 `<工具名>`…”。

这带来两个不足：

1. 同一个项目里的每个破坏性问题，要输入的都是同一个项目名。输过一次之后就成了习惯动作，起不到“看清楚删的是哪一个”的作用。
2. 按钮上是工具名（`eplan_page_delete`），不是工程师的话（“删除页”）。

## 决策驱动因素

- 确认值必须是 Host 给出的结构化数据，不能从文字里解析，也不能由 AI 的调用参数直接决定显示成什么。
- 旧的 Workbench 连新的 Host、新的 Workbench 连旧的 Host，都要能继续审批，只是退回现在的行为。
- 不是每个工具都有单一目标（批量删除、覆盖式导入）；这些情况要有明确的退路。
- 不改变“谁说了算”：是否批准仍由 Host 按请求号、指纹和参数哈希判定，新字段只用于显示和输入确认。

## 备选方案

1. 维持现状：确认值是项目名，按钮是工具名。
2. **给问题加可选的目标字段和动作类别**，由 Host 从写入计划里取。
3. 让 Workbench 从变更清单的文字里解析目标。
4. 确认值改为随机的短码（例如 4 位数字），不依赖目标。

## 决策

**建议选择方案 2**，按下面的规则。

1. `ApprovalAskParams` 增加两个可选字段，协议版本升到 2，最低支持版本仍是 1：
   - `target`：`{ kind, id, count }`。
     - `kind` 是固定的枚举：`page`、`device`、`placement`、`connection`、`part`、`project`、`macro`、`other`。
     - `id` 是这个目标在 EPLAN 里的标识，原样的结构化值（页的完整页名、设备标识、部件号等）；没有单一目标时为空。
     - `count` 是受影响对象的个数，批量操作时大于 1。
   - `action`：固定的枚举，如 `delete`、`renumber`、`overwrite`、`import`、`other`。Workbench 用它和 `target.kind` 从自己的词表里拼出按钮文字（“删除页…”“覆盖部件…”），**文字不由 Host 传**，这样按钮上永远是 Workbench 自己的两种语言的固定词，不会混进项目数据。
2. 字段由 Host 填，来源是写入计划（`WritePlan`）里已经解析过的目标，不是 AI 的原始调用参数。计划里没有的工具先不填，逐个工具补；补的时候每个工具有 Small 测试说明它的目标取自哪里。
3. Workbench 的确认值：
   - 有 `target.id` 且 `count` 为 1：输入 `target.id`。
   - `count` 大于 1：输入个数（例如“12”），面板写明“将影响 12 个页”。
   - 没有 `target`（旧 Host，或还没补的工具）：退回现在的做法，输入项目名称。
4. `target.id` 是项目数据：显示时按现有规则处理成单行纯文本并标“来自项目的数据”；比较时用 Host 给的原值逐字符比较，只去掉首尾空格。含有不可见字符或超过一定长度（建议 64 个字符）时不用它做确认值，退回个数或项目名，并在面板上说明原因。
5. 审计记录里记下问题带的 `target` 和 `action`，方便事后对照；不记工程师输入的内容。
6. 写入问题和解除暂停的问题也可以带这两个字段，只用于显示（队列行和详情里的“目标”一栏），它们的回答方式不变。
7. EPLAN 里的后备对话框（Workbench 不在运行时由插件询问）不在本 ADR 范围：它现在对破坏性问题没有输入确认这一步，是否补上另行提议。

理由：

- 方案 1 的确认值对同一项目永远相同，防不住“顺手输完”。
- 方案 3 把项目里的文字当成结构化数据用，正是 ADR-0035 的风险表里要避免的。
- 方案 4 能防止盲点，但不能让工程师确认“是哪一个对象”；作为没有目标时的退路可以再议，这里先用更简单的项目名。

## 后果

- **好的**：确认面板问的是“删的是哪一个”，每个问题不同；按钮写的是工程师的话；队列和详情能显示目标，也为设计稿里的“目标标识”“影响范围摘要”提供了数据。
- **坏的或要付出的代价**：
  - Host 要逐个工具说明目标，没有补到的工具长期停在退路上；需要一张“哪些破坏性工具已经带目标”的清单并纳入测试。
  - 协议多了一个版本，两端各多一条兼容路径要测。
  - 页名、设备标识可能很长或含特殊字符，输入不便；第 4 条的退路会让一部分问题仍然输入个数或项目名。
  - `kind` 和 `action` 的枚举以后要增加时，旧的 Workbench 会把不认识的值当作 `other`，按钮退回“执行 `<工具名>`…”。
- **后续行动**（接受后）：
  1. 协议：`ApprovalAskParams` 加字段，版本 2，握手和 JSON 的兼容测试。
  2. Host：`WritePlan` 提供目标；先做删除页、删除放置、删除设备三类，再做其余破坏性工具。
  3. Workbench：按钮词表、确认值规则和退路；队列行和详情显示目标。
  4. 审计记录加字段；更新 ADR-0014 的字段表和 ADR-0035 的落实说明。
- **接受前要确认的事**：
  - 批量操作输入个数是否可以，还是批量的破坏性操作一律要求逐个审批；
  - 第 4 条的长度上限；
  - 第 7 条：插件里的后备对话框是否也要补输入确认。

## 各方案利弊

### 方案 1（现状）
- 优点：不改协议。
- 缺点：见“背景与问题”的两个不足。

### 方案 2（加目标字段）
- 优点、缺点：见“后果”。

### 方案 3（解析变更清单）
- 优点：不改协议。
- 缺点：把人读的文字当数据；清单的措辞一改就坏；项目数据可以伪造出看起来像目标的文字。

### 方案 4（随机短码）
- 优点：不依赖目标，所有工具立即可用。
- 缺点：只证明“人在看”，不证明“看的是对的那个对象”。
