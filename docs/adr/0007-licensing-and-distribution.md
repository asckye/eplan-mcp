# ADR-0007：授权与分发：0.x 阶段发布未签名插件，构建预留 EADN 签名开关

| 项 | 内容 |
|---|---|
| 状态 | Accepted |
| 日期 | 2026-10-13（提出并接受） |
| 决策人 | 项目负责人 |
| 门的类型 | 双向门：签名可以随时加上，但对外公布的支持范围要谨慎 |

## 背景与问题
EPLAN 官方文档把编译的 API 程序分为两种授权（[api-notes](../eplan/api-notes.md) B8）：
- **开发者授权**：只加载**未签名**程序，"通常"把项目限制在 5 页以内，只用于开发和测试；
- **运行时授权**：只加载经过 **EADN 签名**的程序。签名需要加入 EPLAN 的开发者计划（EADN），由 Eplan Cloud 的签名服务完成；客户"通过开发者"获得运行时授权。

spike S0 在开发机上实测（[S0 报告](../../spikes/S0-licence/README.md)）：**未签名插件可以加载，并能读写 321 页的项目，没有页数限制**。但这只证明了这一份授权（借用授权，`APIExtension` 可用）。其他用户的授权会怎样，无法在本地验证。

## 决策驱动因素
- 项目目前是个人开源项目，没有加入 EADN，也没有商业分发渠道；
- 开发和测试不能被签名流程拖慢；
- 不能向用户承诺我们没有验证过的支持范围；
- 用户的授权不满足要求时，必须得到明确的诊断，而不是莫名其妙的失败。

## 备选方案
1. **只发布未签名插件**，明确要求用户的授权允许加载未签名的 API 插件。
2. **加入 EADN，所有发布都签名**，面向持有运行时授权的用户。
3. **0.x 阶段发布未签名插件，构建流程预留签名开关**，在 1.0 之前根据用户反馈重新评估。

## 决策
选择**方案 3**：
- 0.x 版本发布**未签名**的 Bridge。README 和发布说明中写明运行要求："需要允许加载未签名 API 插件的 EPLAN 授权（包含 API 扩展）"，并注明已验证的环境。
- `eplanmcp doctor` 增加**授权自检**：报告 `License.Type`、`APIExtension` 是否可用，并在 scratch 项目上做一次"建页面再删除"的实测（自动清理），判断当前授权是否真的能写。
- 遇到授权问题时，Bridge 返回 `LICENCE_MISSING` 或 `LICENCE_RESTRICTED`（新增错误码，例如命中页数限制），并在消息中说明可能的原因。
- 构建中预留 `-p:EplanSign=true` 开关：开启时给 Bridge 加上 `[assembly: EplanSignedAssembly(true)]`，并执行 EADN 签名步骤。在获得 EADN 资格之前，这个开关保持关闭，CI 只验证它能编译通过。
- **重新评估的时机**：发布 1.0 之前；或者有用户报告其授权只能加载已签名程序时。届时另写 ADR，决定是否申请 EADN。

## 后果
- **好的**：不受签名流程阻碍，可以马上开展 M1 后续工作；支持范围诚实，用户有明确的自检手段；需要签名时不用重构。
- **代价**：只持有运行时授权的用户暂时无法使用；持有开发者授权的用户可能遇到 5 页限制（只能通过他们的反馈确认）。
- **后续行动**：
  - 错误码表新增 `LICENCE_RESTRICTED`；
  - `doctor` 的授权自检列入 M1 范围；
  - 收集用户报告的授权类型和结果，记入 api-notes。
