## 背景与问题

项目负责人 2026-10-30 决定：先补齐 EPLAN 官方 API 的全部操作层、官方 action、对象类型和界面 action，完整测试之后再做整个工程的自动绘图。理由是按图纸逐页推进时，每次都会遇到新的缺口。v0.5.0 先按现有能力发布。

覆盖报告（2026-10-30）的现状：

| 口径 | 分母 | implemented | live_verified |
|---|---:|---:|---:|
| 操作层（重载组） | 4014 | 350（8.7%） | 164（4.1%） |
| 对象类型（数据字典） | 68 | 12（17.6%） | 5 |
| 官方 action（按行） | 137 | 7（5.1%） | — |
| 界面 action（MFTools） | 约 1050 | 0 | 0 |

把每个重载组做成一个 MCP 工具不可行：工具设计规范要求工具数量可控、每个工具有明确用途和完整校验，几千个工具会让模型无法选择，也无法逐个写规格和 Large 测试。

## 决策驱动因素
- 负责人要求覆盖全部操作层、action、对象类型；
- 写操作必须可审批、可回滚、可撤销、可审计（ADR-0005、ADR-0010），scratch 之外的写入须人在审批中明确批准（CLAUDE.md 硬性规则 1）；
- 模型给的参数一律不可信（security.md TB1），不能出现"任意方法调用"的后门；
- 不凭名称假设 EPLAN 行为（CLAUDE.md），覆盖必须以实机验证为准；
- 工具数量和描述长度受工具设计规范约束。

## 备选方案
1. 每个功能区写专用工具，直到覆盖全部 API：最安全，工具数以百计，工期以月计，且很多 API 只有少数场景用得到。
2. 只提供反射式的"任意方法调用"：覆盖最快，但等于把 EPLAN API 原样交给模型，绕开参数校验、事务和撤销边界。
3. **通用层 + 专用工具**：对象类型和属性用通用读写，方法和 action 用只读目录加分级执行，配批量实机验证；高频且复杂的功能区另做有类型的专用工具。

## 决策
选择方案 3。

### 一、对象类型：通用读、白名单写
- 新增只读工具（名称按工具设计规范定，例如 `eplan_object_find` / `eplan_object_get`），覆盖数据字典全部 68 种对象类型：按类型、页、名称查找，分页返回对象定位器和属性（属性 ID、名称、索引、值，按语言读取）。
- 属性写入沿用 `eplan_property_set` 的白名单机制：每个属性单独登记可写性、取值校验和读回规则，经验证后加入；不提供"任意属性写入"。
- 对象定位器沿用现有项目身份 + 类型/对象编号 + 摘要机制。

### 二、操作层方法与 action：目录 + 三级执行
- **B 级（只读目录）**：`catalog/eplan-2026.0.3/` 已登记的 4649 个重载组和全部 action 提供搜索与说明（签名、所属类型、文档摘要、排除原因、验证状态）；界面 action 按 ADR-0030 运行时从本机安装读取，不入库。
- **A 级（已验证）**：每个已验证的方法组或 action，经一个专用工具或已有工具的操作暴露，带完整参数校验、事务、撤销和读回；验证记录写进 api-notes，覆盖报告标为 live_verified。
- **C 级（未验证执行）**：只在 scratch 根目录下的项目、每次调用都审批、默认关闭；只接受目录中登记过且未被排除（deprecated、internal、unsafe、GUI 等）的方法组，参数只允许简单值和对象定位器，不允许委托、文件路径之外的任意对象或另一个 action；执行前后做业务快照和文件指纹对比，超时或出现模态对话框报 `unknown` 并暂停写入（ADR-0010）；审计标记"未验证"。
- C 级的方法调用经 Bridge 中按目录生成的分发表执行，不使用基于字符串的任意反射调用；分发表只包含目录中的条目。

### 三、批量实机验证
- 维护者工具在 scratch 副本上逐组试跑：读取类直接调用并比对；写入类在 `SafetyPoint` 中执行，记录是否弹窗、耗时、改动、能否回滚和一步撤销。
- 结果写入覆盖报告（live_verified / env_blocked / 不可回滚）和 api-notes；通过验证的按 A 级流程升级。

### 四、专用工具
对复杂且高频的功能区写有类型的工具，优先顺序待负责人确认：E3D（Pro Panel 3D 与安装板）、Planning、Revisions、Topology、`EServices.Ged`、主数据（部件、表格、图框，与 M9 合并）。

## 后果
- **好的**：全部对象类型可读，全部方法和 action 可查；已验证的能力有完整安全保障；未验证的能力也能在 scratch 中由人逐次把关使用；覆盖率有统一口径，随批量验证持续上升。
- **坏的或要付出的代价**：C 级结果只能比较前后快照，做不到专用工具那样逐项核对；生成分发表和维护目录需要随 EPLAN 版本更新；批量验证需要大量实机时间，且会占用 EPLAN 授权。
- **后续行动**：负责人确认后写设计文档（分批计划、工具清单、规格）；security.md 增加 C 级方法调用的威胁说明；按"对象类型通用读 → 目录 → 批量验证 → C 级执行 → 专用工具"的顺序推进，每一步都有 Small/Medium 测试和 scratch 上的 Large 测试。
