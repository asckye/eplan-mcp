## 背景与问题

Workbench 现在只做三件事：注册插件、配置客户端、回答 Host 发来的审批。它不读项目，也不改项目。审批管道上 Workbench 是服务端，Host 只在需要审批时连过来（ADR-0014），而 Host 是 AI 客户端用 stdio 拉起的，Workbench 打开时不一定有 Host 在运行。

2026-11-20 的 Workbench 4.0 设计稿要求两类新能力：

1. **读项目数据**：项目结构树（结构标识符、页、宏、设备清单、报表）、页内设备、网表、原理图示意、核查结果、正在运行的 EPLAN 实例。
2. **工程师在 Workbench 上直接操作**：导出 PDF/DWG、生成和刷新报表、放置窗口宏、运行项目核查、保存项目、附着或打开项目。

负责人 2026-11-20 对三个方向作了选择：读数据经 Host 只读；人发起的操作走与 AI 相同的工具和审计；检查更新只在手动点击时联网（后者另见 [ADR-0066](0066-manual-update-check.md)）。本 ADR 写明前两项怎么落实。

## 决策驱动因素

- **只有一条通往 EPLAN 的路**：所有读写都经 Host 的工具，事务、读回核对、撤销步骤、备份、审计和写入暂停（ADR-0010）都不另写一份。
- **人点的按钮就是批准**：工程师自己点的普通写入不应再弹一次审批；但破坏性写入、系统主数据写入和解除暂停仍要按 ADR-0035 两步确认。
- **不扩大入口**：Bridge 的管道只给 Host 连（ADR-0002/0003），不给 Workbench 开第二个入口；也不在网络上暴露任何新端口。
- **Host 的审批判定不变**：是否执行仍由 Host 按请求号、指纹和参数哈希判定。

## 备选方案

1. **Workbench 直接连 Bridge 的管道**：少一跳，但 Bridge 多一个客户端，绕开 Host 的策略、审批和审计，要把这些在 Workbench 里再写一份。
2. **Workbench 启动自己的 Host 子进程，作为 MCP 客户端调用工具**（本提议）。
3. **在审批管道上加读取方法**：方向不对。管道上 Host 是发起方，而 Workbench 需要数据时可能根本没有 Host 在运行。

## 决策

采用方案 2：

1. **子进程**：Workbench 在需要数据或操作时启动 `eplanmcp.exe serve`，用 stdio 说 MCP，`clientInfo.name` 为 `EplanMcp Workbench`；它和 AI 客户端拉起的 Host 一样，按现有规则发现 Bridge（ADR-0057）。Workbench 退出时结束它。不开 HTTP，不改 profile。
2. **读取**：只调用带只读注解的工具（`eplan_project_get`、`eplan_page_list`、`eplan_page_get`、`eplan_device_list`、`eplan_connection_list`、`eplan_check_list`、`eplan_session_status` 等）。返回的项目文字一律当数据显示，经 `ProjectText.Line` 转义，不解释、不执行。原理图示意只按读到的设备和连接画示意框，不渲染 EPLAN 图面。
3. **工程师发起的写入**：按钮调用同名工具并明确传 `dry_run: false`，写入前先显示该工具的预览（变更清单），工程师点“执行”才发出。Host 照常经审批管道问 Workbench；Workbench 只在同时满足以下三条时自动回答“批准”，否则照常显示问题：
   - 问题来自自己启动的子进程（握手里的 `HostProcessId` 等于子进程的 PID）；
   - 工具名和参数哈希（`ArgumentsHash`）与 Workbench 刚发出、尚未完成的那次调用一致（参数哈希的计算移到 `EplanMcp.Workbench.Protocol`，Host 与 Workbench 共用一份）；
   - 问题类型是普通写入。
4. **始终要人确认的写入**：破坏性写入、系统主数据写入和解除写入暂停，Workbench 在发出调用**之前**先按 ADR-0035 两步确认（默认拒绝、输入目标标识）；Host 的问题到达后同样只在上面三条匹配时自动回答。没有经过这一步就不发出调用。
5. **审计**：客户端名记为 `EplanMcp Workbench`；审批记录的批准来源记为“工程师在 Workbench 发起”，与“工程师批准 AI 的请求”区分。只加一个可选字段，旧记录不变，哈希链不变。
6. **不做的**：Workbench 不调用 `eplan_api_try`、`eplan_action_try` 和计划执行工具；不做批量或定时操作，每次写入对应一次点击；不在 AI 的会话里插入调用。

## 后果

- 好处：项目页能显示真实数据；导出、报表、核查、保存可以不经 AI 完成，且和 AI 的写入一样可撤销、可审计。
- 代价：Workbench 打开项目页时会多一个 `eplanmcp.exe` 进程，同一个 EPLAN 可能同时连着两个 Host（AI 的和 Workbench 的）；Bridge 本来就按请求串行执行，这一点要在实机上确认不会互相等待过久。
- 风险：自动回答的匹配逻辑一旦写错，可能让 AI 的请求被当成工程师发起而放行。缓解：三条条件缺一不可，并为“PID 不符”“哈希不符”“破坏性”各写反例测试；匹配失败一律回到正常提问。
- 同一 Windows 用户下的恶意程序可以冒充 Workbench 的子进程，这与 ADR-0014 的威胁边界相同，不在防护范围内。

## 实施顺序（接受后）

1. 子进程管理与只读调用；项目页接真实数据（结构树、页、页内设备、网表、核查结果）。
2. 参数哈希移到共享库；自动回答的匹配与反例测试。
3. 导出 PDF/DWG、报表生成与刷新、项目核查、保存；再做放置窗口宏和附着项目。
4. 实机：在 scratch 项目上逐个按钮核对写入、撤销和审计记录。
