# ADR-0054：通用入口的主数据句柄：读不限库，写只在当前配置为 scratch 文件副本时开放

| 项 | 内容 |
|---|---|
| 状态 | Accepted |
| 日期 | 2026-11-12 |
| 决策人 | 项目负责人 |
| 门的类型 | 单向门：开放写入后再收紧，已经写过的副本无法追回 |

## 背景与问题
操作层 4014 组里，`masterdata_copy_pending` 有 660 组：`MDPartsDatabase`、`MDPart`、各种 `MD*Position`、`MDSymbol`、`MDPartsManagement`、`DataModel.MasterData.WindowMacro` 等主数据类型的成员（[覆盖报告](../eplan/coverage-report.md)、`catalog/mapping/operation-gaps.g.tsv`）。[ADR-0033](0033-api-try-object-handles.md) 规定这些句柄"只在 M9 的部件库副本规则下可用"，但这条规则至今没有写成决定，所以通用入口 `eplan_api_try` 一直拿不到它们，这些组只能算"到不了"。

已有的约束：
- [ADR-0019](0019-master-data-writes.md)：写系统主数据按 Destructive 处理，每次审批，先 `backup /TYPE:MASTERDATA`，只支持文件型数据库，从不改 EPLAN 的部件库配置。
- [ADR-0036](0036-settings-and-schemes.md) 第 4 点：部件库优先显式打开 scratch 文件副本；`PartsService.PartsDatabase` 的全局切换仍被禁止。
- 已验证的做法：`eplan_part_build` 2026-11-10 在部件库副本上实机通过。由工程师在 EPLAN 中把部件库配置成隔离副本，工具核对配置路径在 scratch 根目录下、与原库哈希一致，不自动选库。
- 普查事故（2026-11-04）之后，系统主数据有写保护：普查不得写主数据。

这改变通用入口的安全和审批模型，属于 L3，只能提议。

## 决策驱动因素
- 负责人要求 4014 组都能用（2026-11-01）；主数据是最大的一块缺口。
- 绝不写工程师在用的部件库，也不改 EPLAN 的部件库配置。
- 每次写入都要能恢复，审批时工程师看得清改的是哪个库。
- 复用已经实机验证过的副本做法，不引入新的选库机制。

## 备选方案
1. **读不限库，写只在 scratch 副本上开放**：任何文件型或 SQL Server 部件库都可以经通用入口读主数据句柄（只读调用）；写调用只有在 EPLAN 当前配置的部件库是 scratch 根目录下的文件副本时才放行，按 scratch 级别（Write）执行，执行前仍按 ADR-0019 备份；不是副本就返回 `POLICY_DENIED`，说明怎么配置副本。
2. **通用入口自己打开副本**：用 `MDPartsManagement` 显式打开 scratch 目录中的数据库文件，不依赖 EPLAN 的配置。打开指定文件的 API 行为尚未实机验证，可能改动全局配置。
3. **读写都只在副本上**：连读也要求先配置副本。最安全，但查询在用部件库这种日常需求也被挡住。
4. **维持现状**：660 组继续算"到不了"。

## 决策
选择方案 1：
- **读**：主数据类型的只读成员（属性读取、查询、`Get*`）开放给通用入口，句柄按 [ADR-0033](0033-api-try-object-handles.md) 的会话句柄规则管理，用完关闭数据库。
- **写**：只在当前配置的部件库是 scratch 根目录下的文件型数据库时放行。判断与 `eplan_part_build` 相同：配置路径规范化后位于 scratch 根目录下，扩展名为文件型库，不是 SQL Server。每次执行前按 ADR-0019 备份主数据；审批按 scratch 规则（Write 在 scratch 中自动），审批与审计写明库路径。
- **始终拒绝**：改部件库配置（`PartsService.PartsDatabase` 等）、SQL Server 库上的写入、删除整个数据库、把副本复制回原库。
- **宏文件**（`WindowMacro` 等）：读取不限位置；保存只允许写到 scratch 根目录下。
- 方案 2 作为后续：先在 scratch 上实机验证"显式打开指定文件不改全局配置"，结论写进 api-notes，再单独提议。

## 后果
- **好的**：约 660 组从"到不了"变成可调用（只读部分立即可用，写入部分在副本上可用），通用入口能查询和维护部件、符号、宏等主数据；沿用已验证的副本做法，不碰在用库。
- **坏的或要付出的代价**：写主数据要工程师先在 EPLAN 中配置副本，多一步操作；读取会打开在用库，大库可能慢（沿用现有超时）；副本与原库的差异需要工程师自己决定是否回写（工具不做）。
- **后续行动**：
  1. 覆盖生成器：主数据类型的读成员不再标 `masterdata_copy_pending`，写成员标为"仅副本"并在报告中单列。
  2. Bridge：通用入口的主数据写调用加副本检查和 ADR-0019 备份；Small 测试覆盖副本判断、SQL Server 拒绝、配置改动拒绝。
  3. 实机（只在 scratch 副本上）：读取部件、符号、宏各一组；在副本上写一个用户自定义属性并读回，核对原库哈希不变。
  4. 更新 api-notes 与 ADR-0033 的交叉引用。

## 各方案利弊
### 方案 1
- 优点：覆盖最大，规则与 `eplan_part_build` 一致，在用库只读。
- 缺点：读在用库时，打开数据库的开销和锁需要关注。
### 方案 2
- 优点：不需要工程师改配置。
- 缺点：API 行为未验证，风险是悄悄改了全局配置，违反 ADR-0019。
### 方案 3
- 优点：最安全。
- 缺点：日常查询也要先配副本，读的那部分组形同不可用。
### 方案 4
- 优点：不用做任何事。
- 缺点：最大的一块缺口一直挂着，达不到 4014 组都能用的目标。
