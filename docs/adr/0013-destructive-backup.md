# ADR-0013：Destructive 操作前用 `CopyProject` 的快照方式自动备份，备份失败就不执行

## 背景与问题
[ADR-0005](0005-safety-model.md) 规定 Destructive 操作"始终需要审批，执行前自动备份项目"，但没有规定怎么备份、备份失败时怎样处理。[M4 设计](../design/2026-10-20-m4-workflows.md)第二批的 `eplan_page_delete`、`eplan_device_renumber`、`eplan_page_renumber` 要用到它（M4 设计 Q4 已按建议决定：另写本 ADR，接受前第二批不开工）。

spike S8（api-notes A15）说明这件事比原先想的更重要：EPLAN 在写入途中被结束时，事务中已做的修改留在项目里，撤销历史随进程消失。对大范围的修改，备份是唯一可靠的恢复手段。

## 决策驱动因素
- 备份必须在修改之前完成，并且确实能用：一份打不开的备份，比没有备份更危险，因为它让人以为有退路。
- 不能要求工程师关闭项目，也不能锁住项目太久。
- 备份本身不能删除或覆盖任何数据。

## 备选方案
1. **`ProjectManager.CopyProject(项目, 备份路径, CopyMode.Snapshot)`**：得到可以直接打开的项目副本。XML 文档说它以非独占方式复制。
2. **`Backup.Project(…, MakeBackup, …)`**：得到 `.zw1` 归档。文档写明要锁定项目，并且"备份后原项目路径失效"。
3. **Host 直接复制 `.elk` 文件和 `.edb` 目录**：EPLAN 打开着项目，复制到的数据是否一致无法保证。
4. **不备份，只靠事务和撤销**：S8 说明进程死亡时这两者都靠不住。

## 决策
**选择方案 1，前提是 S12 证实它在打开的项目上可用（不可用时见第 7 条）。**

1. **时机**：审批通过之后、执行之前。顺序为：策略 → 审批 → 备份 → `TransactionScope` → 读回 → 提交。
2. **失败即不执行**：
   - 备份失败、超时，或者备份副本的页数与源项目不符，就不执行；
   - 返回新的错误码 `BACKUP_FAILED`（`execution: not_started`，不可重试），提示请工程师检查磁盘空间，或运行 `eplanmcp doctor`。
3. **位置**：`<数据根目录>\backups\<项目名>\<UTC 时间>\`。路径写入审计记录和工具结果（`backup` 字段）。审批对话框注明"执行前会先备份到 …"。
4. **范围**：scratch 中的 Destructive 操作同样备份，与 ADR-0005 一致。
5. **保留**：不自动删除备份，删除本身也是删数据。`doctor` 报告备份占用的空间。
6. **恢复**：不提供恢复工具。工程师在 EPLAN 中打开备份副本，自行决定如何处理（M4 设计非目标）。
7. **S12 不支持方案 1 时**（例如必须关闭项目）：第二批暂停，另写 ADR 比较其余方案，不自动改用方案 2 或 3。

## 后果
- **好的**：
  - 每次 Destructive 操作前都有一份可以直接打开的完整副本，进程死亡或结果不符合预期时都有退路；
  - 失败时一定不执行，不会出现"以为有备份、其实没有"。
- **坏的或要付出的代价**：
  - 每次 Destructive 调用多花备份的时间和磁盘空间（示例项目的大小由 S12 测量）；
  - 审批流水线多一步、多一个错误码；
  - 备份不会自动清理，需要工程师自己管理。
- **后续行动**：
  - spike S12 验证 `CopyProject(Snapshot)`：是否需要独占、副本是否完整可打开、耗时和大小、源项目文件是否变化；
  - Contracts 和错误码表加入 `BACKUP_FAILED`；
  - 审计记录加上 `backup` 字段；
  - `doctor` 报告备份的空间；
  - 本 ADR 接受之前，M4 第二批不开工。
