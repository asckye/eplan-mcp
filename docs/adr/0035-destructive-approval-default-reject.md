## 背景与问题

现行规则要求两个审批按钮样式相同、位置固定、没有默认按钮，也不设快捷键，目的是不引导审批人，防止盲批和误触。对写入问题，这个规则合适：写入可以撤销，审批人应当在两个选项之间中立地判断。

破坏性问题（删除页、删除设备、覆盖主数据等）不一样：执行后不能在 Workbench 里撤销，只能靠执行前的备份恢复。对这类问题，"不引导"反而不够安全：审批人顺手按下的那个键，或者点到的位置，应当总是落在安全的一边。项目负责人的 v2 设计据此给出了新的交互。

## 决策（提议）

只对 Host 标为 `destructive` 的问题生效：

1. **拒绝是默认动作**：拒绝按钮用主要样式，回车键回答"拒绝"。这是现行"不设快捷键"规则唯一的例外，而且只朝安全方向：任何按键都不能批准。
2. **批准分两步**：
   - 第一步，点击"删除页…"这类按钮。它是次要样式，文字是具体动作，不写"批准"，按钮文字由 Host 的问题内容生成。
   - 第二步，打开确认面板。面板写明会一起删除的内容，并说明不能在这里撤销。审批人必须输入确认值（例如页号）。输入正确之前，确认按钮不可用。面板里的默认按钮是"取消"，回车和 Esc 都回到问题，不批准。
3. **倒计时、超时自动拒绝、500 ms 防误触（ResponseGuard）、焦点规则都照旧**。打开确认面板不重置倒计时。
4. **写入问题保持现行规则**：两个按钮样式相同、位置固定，没有默认按钮，也没有快捷键。
5. **Host 侧不变**：审批协议、问题字段、审计记录、`APPROVAL_DENIED` 都不变。Workbench 只是把"批准"多加了一步确认。
6. **"在 EPLAN 中定位"不在本 ADR 范围**：它需要 Workbench 向 Host 或 Bridge 发出新请求，以后单独提议。

## 备选方案

- **维持完全对等**：交互最简单，但破坏性操作的误批风险更高，也不符合 v2 设计。
- **对破坏性问题只加输入确认，不设默认拒绝**：仍然要加确认步骤，却放弃了"按键总落在安全一边"的好处。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 审批人习惯性按回车，把本该批准的删除拒绝了 | 拒绝是安全方向；AI 可以重新请求，审计里会留下拒绝记录 |
| 确认值来自项目数据，可能含误导文字 | 确认值只取 Host 问题里的结构化字段（例如页号），按数据显示，沿用"来自项目的数据"提示 |
| 两类问题交互不同，容易混淆 | 破坏性问题用危险图标和"破坏性"标签，底部提示"点'删除页…'后还要再确认一次" |

## 决定

2026-11-01 项目负责人接受：破坏性问题按上面的两步批准实现，写入问题保持对等；随 ADR-0034 的 Workbench 改版在 v0.5.0 之后实现，同时修订 ADR-0011 第 4 节、ADR-0014 第 6 条、SEC-24 及 workbench-ui 的相关规则。
