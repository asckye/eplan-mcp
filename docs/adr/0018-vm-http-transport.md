## 背景与问题
EplanMcp 现在只有 stdio 一种方式：AI 客户端在同一台电脑、同一个 Windows 用户下启动 `eplanmcp.exe`，Host 再经只允许当前用户、拒绝网络登录的命名管道连接 EPLAN 中的 Bridge（ADR-0003、SEC-03）。工程师常把 EPLAN 装在虚拟机中，AI 客户端却在宿主机上，这种情况现在用不了。

项目负责人 2026-10-20 要求"需要和TIA mcp一样加入虚拟机连接的系统"，并选择"同 TIA，并把防火墙限制到宿主机 IP"，放在 M5 中做。

TIA 的做法（2026-10-20 只读查阅其仓库）：
- **虚拟机中**：TIA 的 MCP 宿主用 ASP.NET Core（Kestrel）和官方 C# SDK 的 HTTP 传输（`WithHttpTransport`、`MapMcp("/mcp")`）提供服务，默认端口 8765。
  - 每个请求的 `Authorization: Bearer <密钥>` 用恒定时间比较（`CryptographicOperations.FixedTimeEquals`），不对就回 401；
  - `/mcp/health` 不需要密钥；
  - 工作台中"网络权限"经 Windows 管理员授权配置防火墙，"启动服务"启动服务，工作台窗口要保持打开；
  - 服务名为 `tia-portal-vm`。
- **宿主机上**：工作台按同一把密钥把 `http://<虚拟机 IP>:<端口>/mcp` 写进各客户端的配置，并提供"测试连接"。
- 导入等工具读的是虚拟机上的文件路径。

## 决策驱动因素
- 安全模型不能因为跨机器而变弱：审批仍只经工程师独立操作的窗口（ADR-0011），写入策略、scratch 和审计仍在 Host 中。
- 网络上的其他机器、宿主机上的浏览器都不能借这个服务操作 EPLAN。
- 与 TIA 的使用方式一致，工程师只学一次。
- 不在宿主机上留下需要维护的服务。

## 备选方案
1. **Host 留在虚拟机中，多一种 HTTP 方式提供 MCP**（TIA 的做法）：Host、Bridge、审批、审计都在虚拟机中，跨网络的只有 MCP 本身。
2. **Host 在宿主机上，把 Bridge 的管道开放到网络**：Bridge 协议没有认证，只靠本机 ACL（SEC-03），开放后等于把 EPLAN 进程交给网络；scratch 判断和导出目录也要跨机器。
3. **经 SSH 启动远程的 stdio**（客户端执行 `ssh <虚拟机> eplanmcp`）：虚拟机要装 OpenSSH 服务器并配置账户和密钥，对工程师太重，也与 TIA 不同。
4. **EPLAN 的 Remote Client**：ADR-0002 已否决（局域网端口未加密、没有认证）。
5. **方案 1 再加 HTTPS（自签名证书）**：密钥和项目数据不再明文传输，但宿主机要信任证书，部分客户端不支持自签名证书。项目负责人选择不加，明文作为剩余风险（SEC-30）。

## 决策
**选择方案 1**（项目负责人 2026-10-21 确认）：

1. **进程**：虚拟机中的同一个 `eplanmcp.exe` 以 `serve --http` 运行；工具、策略、审批（虚拟机中的 EPLAN 对话框或 Workbench）、审计和数据根目录都与 stdio 方式相同，都在虚拟机中。stdio 方式不变。
2. **启动和停止**：只由工程师在虚拟机的 Workbench 中选择"启动服务"后运行。
   - 服务是 Workbench 的子进程，Workbench 退出时一起停止；
   - 安装程序和登录自启动都不会启动它，也不注册 Windows 服务。
3. **传输**：MCP 的 Streamable HTTP，用官方 C# SDK 的 ASP.NET Core 包（`ModelContextProtocol.AspNetCore`，与 SDK 同版本，新依赖按编码规范第 7 节登记）和 Kestrel。
   - 只有一个端点 `/mcp`；
   - 只绑定工程师选择的虚拟机 IPv4 地址，**不监听所有接口**；
   - 默认端口 **8766**：TIA 用 8765，两者可以在同一台虚拟机中同时运行。
4. **认证**：一把共享密钥，256 位随机数（base64url），由 Workbench 生成，在虚拟机中用 DPAPI（当前用户）加密保存在数据根目录中。
   - **每个请求**都要 `Authorization: Bearer <密钥>`，用恒定时间比较；没有不需要密钥的端点（与 TIA 的 `/mcp/health` 不同）；
   - 不对就只回 401，不说明原因；
   - 同一来源地址一分钟内失败 10 次后，该地址的请求一分钟内回 429，并写日志；
   - "重新生成"之后旧密钥立即失效。
5. **Origin**：带 `Origin` 请求头、且不在允许列表中的请求回 403；允许列表默认为空。浏览器总会发这个头，命令行客户端一般不发；这样宿主机上的网页无法借 DNS 重绑定或跨站请求访问服务（MCP Streamable HTTP 传输的安全要求，[规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)）。哪些客户端会发 `Origin`、发什么值，由 S19 逐个核对，必要时把它们的值加入允许列表。
6. **防火墙**：工程师在 Workbench 中选择"网络权限"并在 Windows 的管理员授权中同意后，Workbench 建一条入站规则：
   - TCP、所选端口，只用于 `eplanmcp.exe`；
   - 远程地址**只有宿主机的 IPv4**；
   - 只在域和专用网络配置文件中生效。

   规则可以在 Workbench 中删除，卸载时提示删除。安装本身仍不需要管理员权限（ADR-0016）。
7. **明文**：不加 TLS（项目负责人的决定，同 TIA）。密钥和项目数据在网络上是明文，作为剩余风险写入威胁模型和入门指南：只在宿主机与虚拟机之间的私有网络中使用。
8. **会话**（2026-10-21 修改，[spike S19](../../spikes/S19-vm-http/README.md)）：MCP 2026-07-28 版协议取消了会话，官方 SDK 的 HTTP 传输默认也是无状态的。所以 HTTP 方式不保存任何会话状态，新旧两版协议的客户端都能用：
   - **一个 HTTP 服务只对应虚拟机中的一个 EPLAN 实例**：Workbench 启动服务时选定它，通常只有一个。`eplan_session_select` 在这种方式下只报告这个实例；它退出后工具返回 EPLAN 不可用，不会改连别的实例；
   - SDK 显式设为无状态模式；Host 到这个实例的串行队列由所有请求共用（架构 5.2）；
   - 客户端自报的名称能从请求中取得时使用，取不到时审批中写"未提供"（S19：无状态时 `initialize` 中的名称不会带到后续请求）；
   - 审计记下每个请求的来源地址；审批对话框和 Workbench 在客户端名称旁标出"经网络：<地址>"。
9. **路径**：工具用到的路径都在虚拟机上，包括 scratch 根目录、导出目录和备份；导出的文件留在虚拟机中，`inline` 图片照常返回客户端。入门指南写明这一点。
10. **宿主机一侧**：宿主机上装 EplanMcp 只为用 Workbench 的配置向导（不需要 EPLAN）。
    - 向导选择"虚拟机 ↔ 宿主机"，填写虚拟机地址、端口和同一把密钥；
    - `client-config` 为所选客户端写入名为 `eplan-vm` 的远程服务器（地址和请求头）；不能发送请求头的客户端在这种方式下不列出。Claude 桌面版也不列出：它的配置文件只支持本机服务器，远程服务器只能作为"连接器"由 Anthropic 的后端以 HTTPS 连接（S19）；
    - "测试连接"用密钥执行 `initialize` 和 `tools/list`。

    宿主机的客户端配置文件中的密钥是明文，这是客户端的限制，入门指南提醒不要分享这些文件。
11. **自检**：`doctor` 报告 HTTP 服务是否在运行、绑定的地址和端口、防火墙规则是否存在以及它放行的地址。
    - Host 在监听成功后原子写入本数据目录的 `state/http-<PID>-<随机标识>.json`，包含 Host PID、UTC 进程启动时间、实际绑定的 IPv4 和端口；停止或释放 Host 时删除自己的文件。异常退出的残留文件由 `doctor` 核对 PID 和启动时间后忽略，诊断不删除文件、不发送网络请求。每个服务单独记录，可发现同一数据目录的多个服务；记录不包含密钥。
    - `vm-firewall show|add|remove --port <n> --host-address <IPv4>` 使用 Windows Firewall COM API 和固定规则名 `EplanMcp.Vm.Http`。`show` 与 `doctor` 只读列出同名规则的实际范围；`add`/`remove` 在未提升权限时拒绝，由后续 Workbench 经 UAC 启动。同名规则重复或与端口、宿主机地址、当前 `eplanmcp.exe` 路径及第 6 条范围不符时拒绝修改，避免覆盖或删除其他配置。

## 后果
- **好的**：
  - EPLAN 在虚拟机中、AI 在宿主机上也能用，与 TIA 一致；
  - 审批、策略、scratch、审计都不变，仍在 EPLAN 所在的机器上；
  - stdio 方式不受影响。
- **坏的或要付出的代价**：
  - 多一个网络上的攻击面（TB7）；明文传输的密钥和项目数据可能在局域网中被截获；
  - Host 的自包含发布多了 ASP.NET Core，体积增加，由 spike S19 测量；
  - 防火墙规则需要一次管理员授权；
  - 宿主机的客户端配置文件中有明文密钥。
- **后续行动**：
  - 威胁模型增加 TB7、T24–T27、SEC-27–30；
  - M5 设计增加 4.12 和实施步骤；
  - spike S19（部分完成）：体积多约 26.5 MB，开始监听约 0.15 秒，认证、限流和 Origin 检查按第 4、5 条实测通过，Claude Code 作为远程客户端可用；经 UAC 建防火墙规则和跨机器连接还要实测；
  - Workbench 的"MCP 与客户端"页增加"同一台电脑 / 虚拟机 ↔ 宿主机"两种方式（与 TIA 相同）。
