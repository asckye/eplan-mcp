# ADR-0011：审批只经工程师独立操作的窗口（EPLAN 对话框、Workbench），不用 MCP elicitation

| 项 | 内容 |
|---|---|
| 状态 | Accepted；Workbench 部分由 [ADR-0014](0014-workbench-approval-channel.md) 细化 |
| 日期 | 2026-10-20（提出）· 2026-10-20（接受：项目负责人明确接受"按推荐来做"；负责人同日取消冷却期，当日生效） |
| 决策人 | 项目负责人 |
| 门的类型 | 双向门（1.0 发布前）：渠道可以再增加，但"审批不能由 AI 客户端代答"这一条放宽时要新的 ADR |

## 背景与问题
[ADR-0005](0005-safety-model.md) 第 3 节及其修订定下的审批渠道顺序是：MCP elicitation → Workbench 审批队列（M5）→ EPLAN 内的审批对话框 → 拒绝。spike S4 证实 Claude Code 支持 elicitation 表单，但界面效果还没有人工确认。M3a 的审批（第 8 步、第 12 步）正在实现。

项目负责人要求参考他的 TIA_Portal_Openness_MCP 项目的审批。该项目**有意不用 elicitation**（其 ADR 0003、偏差 MCP-13），只用独立的桌面窗口（WPF Workbench，经同一用户的命名管道）审批。理由是：elicitation 的表单由 AI 客户端自己显示、自己回答。客户端正是驱动模型的那个程序，它可以在无界面模式下运行（`claude -p`、Agent SDK），也可以被设置为自动回答。所以表单上的"批准"并不能证明有人确认过。

审批要防的正是模型出错或被项目中的文本诱导（威胁 T11）。如果批准可以由客户端代答，这道防线就和客户端的配置绑在了一起。

## 决策驱动因素
- **审批必须是人的独立操作**：不能由 AI 客户端、模型或脚本代答。
- **审批针对具体的变更清单**：先规划再审批，审批后比对指纹（ADR-0005，不变）。
- **适用于任何 MCP 客户端**：包括不支持 elicitation 的客户端，以及无界面运行的代理。
- **实现和验证尽量简单**：S4 的界面确认至今没有完成，是 M3a 的阻塞项之一。

## 备选方案
1. **维持现状**：elicitation 优先，其次 Workbench、EPLAN 对话框。
2. **只用独立窗口**：Workbench（M5，运行时优先）→ EPLAN 内的审批对话框 → 拒绝。不用 elicitation 审批；等待期间用 MCP 进度通知告诉客户端"请在 EPLAN 中审批"。
3. **两者都要**：先在客户端确认，再在 EPLAN 中确认。

## 决策
**选择方案 2。**

1. **渠道**：
   - Workbench 审批队列（M5，Workbench 正在运行时）；
   - 否则 EPLAN 内的审批对话框：模态窗口，所有者是 EPLAN 主窗口，闪烁任务栏提醒；
   - 都不可用时拒绝。

   elicitation 不用于审批，也不用于解除写入暂停（ADR-0010 第 3 节）。
2. **等待**：
   - 工具调用在 Host 中等待决定。客户端提供了进度令牌时，每 15 秒发一次进度通知，说明正在等待 EPLAN 中的审批；
   - 期限默认 120 秒，`config.json` 可在 60–300 秒之间设置；
   - 到期按"已过期"拒绝（`APPROVAL_EXPIRED`）。
3. **请求与决定的绑定**（借鉴 TIA）：
   - 请求 ID 由 Host 生成，从不采用客户端给的值；
   - 决定绑定请求 ID、计划指纹和参数摘要，只能使用一次；
   - 迟到、重复或不匹配的回答一律视为拒绝。
4. **对话框**：
   - 显示工具、项目和变更清单（过长的值截短，机密不显示），并注明可以在 EPLAN 中按 Ctrl+Z 撤销；
   - "批准""拒绝"两个按钮一样大，都不是默认按钮，没有直接批准的快捷键；
   - 出现后 500 毫秒内的点击无效，防止误触；
   - 显示自动拒绝的倒计时；
   - 文字跟随系统界面语言（M3 设计 4.6）。
5. **结果与审计**：
   - 区分已拒绝、已过期、无可用渠道、已取消几种结果；
   - 每个决定单独写一条审计记录，用请求 ID 与该次写入关联。
6. **不变的部分**：
   - ADR-0005 的分级、策略引擎；
   - 先规划再审批；
   - 执行前比对指纹（`PLAN_STALE`）；
   - 拒绝、取消、超时都不执行。

## 后果
- **好的**：
  - 审批不依赖 AI 客户端的实现和配置，无界面运行的代理也无法代答；
  - 任何 MCP 客户端都能用；
  - S4 的界面确认不再是阻塞项。S4 在协议层的结论仍然有效，只是不再用于审批；
  - Host 不需要多轮请求的审批状态。
- **坏的或要付出的代价**：
  - 工程师要切换到 EPLAN 窗口去点批准；
  - 对话框打开期间 EPLAN 界面被占用，其他调用返回 `EPLAN_BUSY`（M3 设计 4.7，原本如此）；
  - 工具调用会挂起到工程师回答为止，依赖客户端的工具超时足够长，靠进度通知缓解；
  - 无界面运行时，真实项目上的写入一律被拒绝。这符合意图：没有人就没有审批，scratch 中的写入不受影响。
- **后续行动**：
  - ADR-0005 第 3 节的渠道顺序标注"由 ADR-0011 取代"；
  - M3 设计 4.3、4.6、7、8 中的 elicitation 审批改为本 ADR 的渠道；
  - 第 7 步已合并的 `PendingPlanStore`（`requestState`）不再用于审批。等审批实现后，如果确实没有其他用处，就删掉；
  - spike README 中 S4 的"待人工确认"改为"不再需要"；
  - 威胁模型 SEC-01、SEC-06 的说明随之调整。

## 各方案利弊
### 方案 1：维持现状
- 优点：工程师在对话中就能批准，不用切换窗口。
- 缺点：批准可以由客户端代答；依赖客户端对 elicitation 的支持和显示效果，S4 尚未确认；需要多轮请求的签名状态。

### 方案 2：只用独立窗口
- 优点：人的确认独立于 AI 客户端；实现简单；与 TIA 项目一致，工程师在两个工具中的体验相同。
- 缺点：要切换窗口；调用会挂起。

### 方案 3：两者都要
- 优点：最稳妥。
- 缺点：每次写入点两次。独立窗口已经足够，客户端的那次确认并没有增加安全性。
