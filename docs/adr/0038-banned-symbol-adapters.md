# ADR-0038：以逐符号写适配器审阅禁用 API，保留禁止表默认约束

| 项 | 内容 |
|---|---|
| 状态 | Accepted |
| 日期 | 2026-11-01 |
| 决策人 | 项目负责人（2026-11-01 接受） |
| 门的类型 | 单向门：扩大安全或审批边界后，调用者会依赖；收回需迁移 |
| 级别与影响 | L3；提议对 ADR-0005/0032 的此类限制建立精确例外；接受后按本文边界逐组实施 |

## 背景、范围与风险

负责人目标是 4014 组全部可调用（scratch、逐次审批）。[缺口清单](../eplan/operation-gap-inventory.md)与 [TSV](../../catalog/operation-gaps.tsv)中本类首阻为 **36 组**；计数不等于该类全部重载，也不重复计其他块的交叉约束。

包括 `Article.LoadFromMasterdata`、`PrjMessagesCollection.Add/Clear`、`ProjectMessage.SetDone`、`Search.Project/Replace`、`Check.VerifyInstallationSpace`、`ActionManager`、`CommandLineInterpreter`。B1 的 `MDPartsDatabase.AddPart/RemovePart`、`Synchronize.PartToSystem` 等也命中禁止表，仍须交叉满足主数据规则。

BannedSymbols 明确记载“看似读取、实际写入”的 API：加载部件写项目、查询/检查写结果库、共享过滤器改变其他读取结果；ActionManager/命令行可转发任意 action，越过目录、审批及路径保护。全局删除禁止项会让所有适配器失去编译期防护。

## 提议的安全调用方式

1. 保持禁止表，逐符号核对其真实副作用与官方/实机证据；仅在一个专用、有类型的适配器内对精确调用行压制 RS0030，并注明理由和证据。通用生成器不能因为负责人接受本类别就整体解除 banned_symbol。
2. 项目写入按真实 Write/Destructive 级别执行，scratch 逐次审批，快照/备份、事务、读回、恢复和审计齐全；查询结果库、消息、共享过滤器另做前后快照，不能仅比较图纸对象数量。主数据调用先满足 B1、ADR-0019/0033。
3. 审批列出“此 API 原在禁止表中”、真实副作用、目标项目/结果库及变更范围。ActionManager 只能到现有经批准目录/白名单的封闭 action + 参数集合，继续拒绝嵌套任意 action、脚本、注册和安全设置修改；字符串命令行不作为绕过入口。

所有候选继续默认关闭，使用随产品审阅的精确编译分支；调用前独立窗口逐次审批，展示 unverified、签名、参数、来源及超出 scratch 的具体效果，绑定实例、输入摘要和前置状态；拒绝/取消/过期不执行。审计先行，不能由模型代答或修改策略；审批不免除同项目/路径/许可等独立前提。结果未知或恢复失败沿 ADR-0010 暂停相应目标和实例，不自动重发。

## 仍不能开放的部分

任意 action 名称、任意命令行、修改安全策略或自动压制整个类型的安全检查不开放。一个禁止成员的公开替代调用不等于原组已被调用，必须如实保留缺口；缺少副作用证据只记录待验，不据此声称有违规。

## 备选方案与代价

维持全部禁止最省实现但留下缺口；全局删除 BannedSymbols 覆盖最快而失去边界；逐符号专用适配器较慢，却能保留其他代码的编译检查和准确审批。

## 需要项目负责人决定

是否接受逐符号、逐适配器的例外流程，并保留全局禁止表？优先开放消息/搜索等项目内写入，还是部分调用永不直接开放？是否确认任意命令行/任意 action 仍不属于目标可调用方式？

本 ADR 只提出该类别的审阅边界；请分别选择接受、修改或维持排除，并记录日期、明确范围和确认原话。其他九类不随之获准；需要逐组例外时另留批准记录。接受前不修改安全标准或运行时策略，不将不可执行项抵充 4014 完成数。

## 决定（2026-11-01）

项目负责人 2026-11-01 确认原话：“按你推荐的来，接受 ADR-0036 到 0045”。按本文“提议的安全调用方式”接受；“仍不能开放的部分”继续排除，也不抵充 4014 完成数。所有候选仍默认关闭，按随产品审阅的精确编译分支逐组开放；逐次审批、scratch 限定与实机验证要求不变。本决定只接受本类别的审阅边界，逐组例外仍须留下批准记录。

## 后续验证与依据

Small 校验精确白名单与实际写级别；Medium 验证未登记符号/参数被挡及审批绑定；Large 验证消息/搜索结果副作用、失败恢复、原撤销历史，主数据另经独立批准。

本次仅离线文档盘点，以上机制均为待验证提议，未运行 EPLAN，也不宣称备份、恢复或看门狗已实现。实现前把精确 API 行为的官方/获准 scratch 证据写入 [api-notes](../eplan/api-notes.md)，新增 Large 待验记入[台账](../process/large-pending.md)。缺失或不可读数据只给警告和证据缺口，不据此判违规；独立成立的写保护、审批、权限及恢复前提仍有效。
