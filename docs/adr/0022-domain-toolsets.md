## 背景与问题
[API 能力覆盖设计](../design/2026-10-21-api-capability-coverage.md)要求官方 API 的每项能力都能追溯到实现、访问路径、证据或不做的理由。能力仍按任务设计成工具（ADR-0006），但第 2 到第 7 阶段会覆盖图形、3D、拓扑、主数据、PLC、翻译、修订等领域，任务工具会从现在的 47 个继续增加。

现在只有两个 Profile：`core`（明确列出的 25 个）和 `full`（全部，默认）。问题：
- 工具一多，`full` 的工具定义要占大量 token，模型也更难选对工具（ADR-0006 的背景）；
- `core` 是一份固定清单，做 3D 布局的工程师要么用 `full`，要么缺工具；
- 客户端对 MCP 工具列表变更的支持不一样。MCP 2026-07-28 中，服务器在工具列表变化时发 `notifications/tools/list_changed`，客户端要先用 `subscriptions/listen` 订阅 `toolsListChanged`。已知 Claude Code 2.1.295 会订阅（[api-notes](../eplan/api-notes.md) C 节，spike S4）；其他客户端是否订阅、收到后是否重新拉取列表，没有核实。

## 决策驱动因素
- **不支持动态发现的客户端必须照常可用**，不能依赖工具列表变更通知。
- **工具契约就是 API**：分组不能改变工具的名称、schema 和注解；`tools/list` 的顺序固定（有利于客户端缓存提示词）。
- **加载不是授权**：让一个工具出现在列表中，不放宽任何审批；Destructive 工具每次审批，`eplan_action_run` 仍要 `actionRun: on`（[ADR-0021](0021-action-run-whitelist.md)），模型给的参数一律不可信（[security.md](../standards/security.md) TB1）。
- **省 token、选得准**：大多数会话只用一两个领域。
- **简单**：不要求客户端和服务器保存额外的会话状态（MCP 2026-07-28 是无状态协议）。

## 备选方案
1. **维持现状**：只有 `core` 和 `full`。
2. **静态工具集**：工具按领域分组，启动时用参数或配置选择要提供的工具集，运行中不变。
3. **动态工具集**：在方案 2 之上，增加列出和加载工具集的元工具，加载后发工具列表变更通知。
4. **网关元工具**：只提供"搜索能力"和"按名称调用能力"两个工具，参数作为任意对象传入。
5. **完全依赖客户端的工具搜索**：始终列出全部工具，由客户端延迟加载（客户端支持时）。

## 决策
选择**方案 2，加上可选的方案 3**。

### 1. 工具集
- 每个工具属于且只属于一个工具集，工具集按领域命名，在代码中明确列出（与现在的 `ToolProfiles.Core` 一样），名称为小写加下划线。初步划分（实现时定稿）：

  | 工具集 | 内容（示例） |
  |---|---|
  | `session` | `eplan_session_status`、`eplan_session_select`、`eplan_tool_usage`；**总是提供** |
  | `project`、`page`、`device`、`connection` | 项目、页、设备、连接的读写 |
  | `cable_terminal`、`plc` | 电缆、端子、PLC |
  | `part`、`macro_symbol` | 部件库、宏与符号（主数据） |
  | `check_report`、`export`、`import` | 检查与报表、导出、导入 |
  | `translation`、`revision` | 翻译与语言、修订 |
  | `panel3d` | Pro Panel 3D（第 5 阶段） |
  | `action` | `eplan_action_run`，仍受 `actionRun` 开关控制 |

- 工具集与覆盖设计的阶段和目录中的命名空间对应，但不要求一项能力一个工具。

### 2. Profile 由工具集组成
- `full`：全部工具集，仍是 `serve` 的默认值，行为与现在相同。
- `core`：不变，仍是明确列出的不超过 25 个工具（`core` 跨工具集挑选常用工具，不按整个工具集选择）。
- 新增 `serve --toolsets <名称,名称,…>` 和 `config.json` 中的 `toolsets`：只提供列出的工具集加上 `session`。未知名称时拒绝启动，并列出合法的名称。
- `tools/list` 的顺序：先按工具集在代码中的顺序，再按名称。任何选择下的列表，都是 `full` 列表的子序列。

### 3. 按需加载（可选）
- `serve --toolsets dynamic`：启动时只提供 `session` 和两个元工具：
  - `eplan_toolset_list`（Read）：列出每个工具集的名称、一句话说明和其中的工具名；
  - `eplan_toolset_load(toolset)`（Read）：把一个工具集加入列表，然后发 `notifications/tools/list_changed`。
- 只加不减：会话中不卸载工具集，避免模型正在用的工具消失。
- 客户端没有订阅工具列表变更时，`eplan_toolset_load` 不加入工具，返回 `INVALID_ARGUMENT`，`message` 说明"客户端不支持工具列表变更，请用 `--toolsets <名称>` 或 `--profile full` 启动"。
- `dynamic` 只在客户端配置中显式写出才生效，默认不用。`client-config` 为已经验证过的客户端写出它，其余客户端写 `full`。
- 加载工具集只是让工具出现在列表中，不改变策略、审批和审计。加载记入日志，不写审计（它不接触 EPLAN）。

### 4. `eplan_tool_usage`
`tool` 枚举只列出当前提供的工具，与 `core` 现在的做法相同；动态模式下加载工具集后一起更新。

## 后果
- **好的**：
  - 不支持变更通知的客户端用 `full`、`core` 或 `--toolsets`，与现在一样可用；
  - 工程师可以只给某个领域的工具，token 更省，模型选得更准；
  - 工具的名称、schema、注解都不变，契约快照中只多出每个工具所属的工具集；
  - 支持变更通知的客户端（已知 Claude Code）可以从很小的工具列表开始。
- **坏的或要付出的代价**：
  - 动态模式下，模型要多一次调用才能拿到某个领域的工具；
  - 工具集的划分本身要靠评测检验，名称一旦写进客户端配置就不好改；
  - 多一个启动参数和配置项，`doctor` 要显示当前的选择。
- **后续行动**：
  - spike：核实 Claude Code、Claude 桌面版和其他常用客户端是否订阅 `toolsListChanged`、收到通知后是否重新拉取工具列表，结论写进 api-notes C 节；
  - 两个元工具先按[模板](../templates/tool-spec.md)写工具规格；
  - 更新工具设计规范第 10 节和架构 5.2；
  - 测试：Small（每个工具恰好属于一个工具集，`core` 不超过 25 个，任何选择下的顺序都是 `full` 的子序列，未知名称拒绝启动）；Medium（动态模式下加载后发出变更通知，未订阅时拒绝加载）；Agent 评测（模型在动态模式下加载正确的工具集，并且不因项目中的注入文本加载无关的工具集）。

## 各方案利弊
### 方案 1：维持现状
- 优点：没有新机制。
- 缺点：工具增加后 `full` 越来越重，`core` 越来越不够用。

### 方案 2：静态工具集（选择）
- 优点：所有客户端都能用；顺序固定；实现简单。
- 缺点：要在启动前决定领域，会话中途不能扩展。

### 方案 3：动态工具集（可选地选择）
- 优点：列表从很小开始，用到哪个领域再加载。
- 缺点：依赖客户端的变更通知；多一次调用；要处理未订阅的客户端。

### 方案 4：网关元工具
- 优点：工具列表只有两个工具。
- 缺点：模型看不到每个能力的 schema 和注解，客户端无法按注解提示风险；参数没有约束；等于 ADR-0021 否决的"任意运行器"。否决。

### 方案 5：完全依赖客户端的工具搜索
- 优点：服务器什么都不用做。
- 缺点：只对支持延迟加载的客户端有效，其他客户端仍要承担全部工具定义。可以与方案 2 并存，但不能代替它。
