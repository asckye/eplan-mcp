# ADR-0019：部件库、翻译库的写入按 Destructive 处理：每次审批，先备份主数据，只支持文件型数据库

| 日期 | 2026-10-21（提出）· 2026-10-21（接受：项目负责人："你刚刚的建议按照你推荐的来即可"） |

| 门的类型 | 单向门：写系统主数据的工具发布后，放宽要求需要新的 ADR |

## 背景与问题
项目负责人 2026-10-21 要求加入部件库管理和项目翻译（[M4c 设计](../design/2026-10-21-m4c-more-tools.md)）。其中下列操作写的是系统主数据，而不是项目：
- 把文件导入部件库（`partslist /TYPE:IMPORTTOSYSTEM`、`partsmanagementapi /TYPE:IMPORT`）；
- 把项目中的部件加入部件库（`synchronize /TYPE:PARTSTOSYSTEM`）；
- 把文件导入翻译库（`translate /TYPE:IMPORTTOTRANSDB`）。

[ADR-0005](0005-safety-model.md) 的级别只区分 scratch 项目和真实项目，没有覆盖系统主数据。主数据与项目有三点不同：
1. 所有项目共用；部件库还可能是团队共用的 SQL Server 数据库，写错了会影响其他人。
2. `SafetyPoint` 和 Ctrl+Z 只作用于项目，管不到主数据，写入途中失败时没有回滚。
3. 没有"scratch 部件库"的概念，Host 也无从判断一个库是不是测试用的。

这改变安全和审批模型，属于 L3，只能提议。

## 决策驱动因素
- 工程师要能维护在用的部件库和翻译库，否则这组工具没有用处。
- 每次修改都要能恢复，而且恢复方法事先验证过。
- 不能影响本机之外的人。
- 审批时工程师要清楚改的是哪个库、影响所有项目。

## 备选方案
1. **按 Destructive 处理**：每次审批；执行前用 EPLAN 的 `backup /TYPE:MASTERDATA` 备份主数据；只支持文件型数据库，SQL Server 上的库一律拒绝。
2. **只允许写测试库**：在 `config.json` 中列出可以写的库，其他一律拒绝，与 scratch 根目录相同。
3. **只审批，不备份**。
4. **不写主数据**：只提供部件库的查询和导出。

## 决策
选择方案 1：
- 写入目标新增"系统主数据"一类，级别为 Destructive：每次审批，scratch 项目中发起的也一样。审批对话框写明库的类型和路径，以及"影响使用这个库的所有项目"。
- 审批之后、执行之前，用 `backup /TYPE:MASTERDATA`（部件库 `MDTYPE:ARTICLES`，翻译库 `MDTYPE:LANGUAGES`）备份到 Host 新建的空目录 `<数据根目录>\backups\masterdata\<UTC 时间>\`。备份失败、超时或者备份文件为空，就不执行，返回 `BACKUP_FAILED`（`execution: not_started`）。备份路径写入审计和工具结果，不自动删除（同 ADR-0013）。
- 只支持文件型数据库。当前库在 SQL Server 上时拒绝（`POLICY_DENIED`），理由写在 `message` 中：本机无法备份，也可能影响其他人。
- 只写工程师在 EPLAN 中配置的那个库，从不改动这项配置：`PartsService.PartsDatabase`、`Translate.TranslateDatabase` 的设置会改全局用户设置（XML）。翻译库也只能这样，API 不能指定翻译库文件。
- `config.json` 新增 `masterDataWrites`：`approve`（默认，按上面的规则执行）或 `deny`（一律拒绝）。与 `writesOutsideScratch` 一样只能通过配置文件修改（SEC-02），`doctor` 显示当前值。
- **前提**：spike S24 证实 `backup MASTERDATA` 在 Bridge 中可用，并且能按备份恢复，恢复步骤写进入门指南。S24 不能证实时，本 ADR 回到讨论，不进入实现。

## 后果
- **好的**：
  - 工程师可以让代理维护在用的部件库和翻译库；
  - 每次写入都有人确认、有备份；
  - 团队共用的库不会被一台机器上的代理改动。
- **坏的或要付出的代价**：
  - 恢复不是一步撤销，要按备份手工恢复；
  - SQL Server 上的库不能用这组写工具；
  - 主数据的备份可能很大，`doctor` 报告占用的空间。
- **后续行动**：
  - S24：已完成（2026-10-21，api-notes A30）。前提成立：`backup MASTERDATA` 在调度器中可用，按备份能恢复。还原不覆盖已有文件，恢复步骤见 [S24 结论 6](../../spikes/S24-master-data/README.md#结论)；部件库 API 的事务不能撤回删除和导入，失败时一律按备份恢复；导入、同步的实机测试会写正在用的库，只能经项目负责人批准后运行（S24 r11）；
  - 威胁模型加入 T29 和 SEC-32；
  - `PolicyEngine` 的决策表加入"系统主数据"目标；
  - `doctor` 显示当前的部件库和翻译库，以及 `masterDataWrites`；
  - 入门指南写恢复步骤。

## 各方案利弊
### 方案 1
- 优点：能维护在用的库；有备份；不影响他人。
- 缺点：恢复靠手工；依赖 S24 的结论。

### 方案 2
- 优点：最安全，与 scratch 根目录的思路一致。
- 缺点：工程师最终要维护在用的库，只能写测试库时，这组工具只能用来试验。

### 方案 3
- 优点：简单。
- 缺点：写错了没有退路，违反 ADR-0005 对 Destructive 操作"先备份"的要求。

### 方案 4
- 优点：没有新的风险。
- 缺点：不满足项目负责人的要求。
