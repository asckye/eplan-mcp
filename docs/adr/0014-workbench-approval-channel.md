# ADR-0014：Workbench 作为单独的进程，在每个用户、每个数据根目录一个的命名管道上接收 Host 的审批

## 背景与问题
ADR-0011 规定审批只经工程师独立操作的窗口：Workbench 正在运行时用它的审批队列，否则用 EPLAN 内的对话框，都不可用时拒绝。它没有规定 Workbench 是什么进程、Host 怎样发现它、怎样把问题交给它、怎样判断"正在运行"。这些是进程拓扑、IPC 和审批模型的决定，属于 L3（[开发流程第 3 节](../process/development-workflow.md#3-变更分级与设计产物)）。详细设计见 [M5 设计](../design/2026-10-20-m5-operability.md) 4.4、4.6。

现状：Host 的 `ApprovalService` 按注册顺序询问渠道，渠道返回 null 表示"现在不能问"，换下一个；决定的绑定（请求 ID、计划指纹、参数摘要）、期限和"只能使用一次"都在 Host 中判断（SEC-06）。一台机器上可以同时有多个 Host（每个客户端会话一个），它们都写同一个数据根目录（ADR-0008）。

项目负责人的 TIA 项目已有同样的审批：WPF Workbench 是命名管道的服务器，主机每次写调用连接一次（连接超时 250 毫秒），管道名由用户 SID 和设置文件的路径算出，第一个实例独占管道名，Workbench 不在时拒绝，主机从不启动 Workbench；核对对端的映像路径，并写明这只防构建错配，不防同一用户的恶意程序（TIA 的 ADR 0003、`ApprovalPipe.cs`、`LocalPipeSecurity.cs`）。

## 决策驱动因素
- 回答必须来自工程师独立操作的窗口（ADR-0011），一个问题只出现在一个窗口中，不能两处都能回答。
- 绑定、期限和一次性仍只在 Host 中判断，Workbench 出错或被替换时最坏是"不执行"。
- 多个 Host 共用一个 Workbench；Workbench 随时可能启动、退出、崩溃。
- MSIX 客户端启动的进程会继承文件重定向（api-notes A6）；无人值守的代理不应在桌面上弹出程序。
- 与 Host–Bridge 的做法一致，便于测试（ADR-0003、ADR-0008）。

## 备选方案
1. **Workbench 是管道服务器，Host 每次审批连接一次**（TIA 的审批管道）。
2. **Host 是管道服务器，Workbench 枚举 Host 并取走问题**（与 Host 发现 Bridge 的方向相同）。
3. **问题和回答写成数据根目录中的文件**，Workbench 监视目录。
4. **Host 需要审批时自己启动 Workbench**（或一个审批窗口）。

## 决策
**选择方案 1。**

1. **进程**：Workbench 是独立的桌面程序 `app\workbench\EplanMcp.Workbench.exe`，由工程师启动或登录时自启动。**Host 从不启动 Workbench**。每个 Windows 用户、每个数据根目录最多一个 Workbench。
2. **管道**：
   - 名称 `EplanMcp.Workbench.1.<摘要>`，摘要是"用户 SID + 换行 + 规范化的数据根目录完整路径（大写）"的 SHA-256 前 32 位十六进制。不同用户、不同数据根目录（例如 Large 测试的临时数据根目录）互不相见。
   - Workbench 用第一个实例标志创建（`FILE_FLAG_FIRST_PIPE_INSTANCE`），名字已被占用时 Workbench 报错并不接收审批；ACL 只允许当前用户，拒绝网络登录，所有者为当前用户（与 Bridge 的 `SecurePipeFactory` 相同）。
   - Host 以 `PipeOptions.CurrentUserOnly` 连接，连接超时 250 毫秒；连上后取服务器进程号，核对它的映像路径是 Host 所在目录下的 `workbench\EplanMcp.Workbench.exe`。Workbench 同样核对连接方是同一安装中的 `eplanmcp.exe`。这只防错配（开发构建连上安装的版本、别的程序占了名字），**不是认证**：同一用户的程序不在防护范围内（[security.md](../standards/security.md) 第 2 节）。
3. **协议**：帧格式和 JSON-RPC 2.0 与 Host–Bridge 相同（ADR-0003），单帧上限 1 MiB，未知字段和重复字段一律拒绝。协议版本是整数，从 1 开始，Host 支持 N 和 N-1。消息：
   - `handshake`：双方的协议版本和程序版本、Host 的进程号；Workbench 回答是否接收新问题（等待中的问题达到 50 个时不接收）；
   - `approval.ask`：请求 ID、问题种类（审批或解除暂停）、工具、级别、项目、EPLAN 实例、客户端自报的名称、变更清单、备份目录（Destructive）、暂停记录（解除暂停）、计划指纹、参数摘要、期限；回答为请求 ID、指纹、参数摘要和决定（批准、拒绝、关闭、过期）；
   - `cancel`：客户端取消了调用，Workbench 移除这个问题；
   - `approval.outcome`（通知）：执行结果，只更新 Workbench 中"已回答"的显示，**不能批准任何东西**。
4. **渠道的选择**（ADR-0011 的顺序不变）：`WorkbenchChannel` 排在 EPLAN 对话框之前。管道不存在、连接超时、映像路径不符、协议不兼容、Workbench 不接收新问题时返回 null，由 EPLAN 对话框询问。**问题一旦送达 Workbench，就只在那里回答**：连接断开按"已取消"处理，不执行，也不转到 EPLAN 对话框。没有配置项可以改变这个顺序。
5. **等待**：Host 等到期限之后再加 15 秒的余量。等待期间不占用 Host 到 EPLAN 的队列；工程师在此期间修改了项目，由执行前的指纹比对发现（`PLAN_STALE`）。期限、绑定和一次性仍按 ADR-0011 第 3 节在 Host 中判断：迟到、重复、不匹配的回答都视为拒绝或过期。
6. **界面**：ADR-0011 第 4 节的规则全部适用，另加队列的规则：每个问题单独回答，没有"全部批准"；两个按钮样式相同（不用强调色）；问题显示或切换时焦点在标题上；**每次显示一个不同的问题、窗口每次由隐藏变为可见之后**，500 毫秒内两个按钮都不响应；客户端名称标注"未验证"；变更清单按纯文本显示，剥除控制字符和双向文字控制符。窗口不抢焦点。
7. **审计**：渠道名 `workbench`；其余与 ADR-0011 第 5 节相同。

## 后果
- **好的**：
  - Host 只多一个渠道类，`ApprovalService` 和绑定规则不变；Workbench 不在时行为与现在完全相同。
  - 审批不再占住 EPLAN：其他调用不会因为等待审批而返回 `EPLAN_BUSY`，工程师可以先在 EPLAN 中查看再回答。
  - 多个 Host 的问题集中在一个队列中；Workbench 重启不影响 Host。
  - 与 TIA 一致，工程师在两个工具中的体验相同。
- **坏的或要付出的代价**：
  - 多一个进程、一个管道协议和一组测试；Workbench 要处理多个同时到达的问题。
  - 映像路径只防错配。同一用户的程序（包括代理经客户端 shell 工具执行的命令）可以冒充 Workbench，也可以操作任一个审批窗口，这与 EPLAN 对话框的情况相同，作为剩余风险记入威胁模型（M5 设计 Q9）。
  - Workbench 在显示问题后崩溃时，这次调用按"已取消"失败，模型要再调用一次。
- **后续行动**：
  - 威胁模型增加 Host ↔ Workbench 的信任边界和对应的威胁、措施（T19–T21、SEC-22–24）；
  - spike S16：窗口不抢焦点时工程师能否注意到新问题，托盘和系统通知，讲述人；
  - 架构 5.1、5.2、6.3 补上 Workbench 进程和渠道的说明；ADR-0011 的状态栏注明"Workbench 部分由 ADR-0014 细化"；
  - `doctor` 报告 Workbench 是否在运行，以及下一次审批会用哪个渠道。

## 各方案利弊
### 方案 2：Host 当服务器
- 优点：Workbench 能列出全部在运行的 Host，不必等它们来问。
- 缺点：每个 Host 多开一个服务器；Workbench 要发现动态增减的 Host（按进程号和随机值命名，像 Bridge 那样）；Workbench 不在时 Host 也不知道该不该等，"正在运行"的判断更复杂。
### 方案 3：文件
- 优点：最简单，不需要管道。
- 缺点：任何能写数据根目录的程序都能写一份"批准"，没有对端可以核对；要轮询、处理半写的文件和清理。
### 方案 4：Host 启动审批窗口
- 优点：工程师不必事先打开 Workbench。
- 缺点：由 MSIX 客户端启动的 Host，其子进程继承文件重定向（A6）；无人值守运行时也会在桌面上弹出窗口；每个 Host 一个窗口，就不是队列了。
