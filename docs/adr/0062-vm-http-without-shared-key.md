# ADR-0062：虚拟机 HTTP 不再用共享密钥，由只放行宿主机的防火墙规则加 Host 头和 Origin 校验把关（修订 ADR-0018）

## 背景与问题

ADR-0018 让虚拟机中的 Host 以 HTTP 提供 MCP：绑定一个 IPv4 地址和端口，每个请求都要 `Authorization: Bearer <密钥>`，一分钟内失败 10 次的来源被锁定一分钟，另有只放行宿主机 IPv4 的 Windows 防火墙入站规则，以及 Host 头和 Origin 校验。

密钥带来的使用负担：要在虚拟机里生成、复制到宿主机、写进每个客户端的配置；客户端配置文件里是明文；Claude 桌面版等不支持自定义请求头的客户端不能用。Workbench 重新设计时（2026-11-20），项目负责人决定去掉共享密钥。

## 决策驱动因素

- 连接虚拟机的步骤越少越好；支持的客户端越多越好。
- 传输本来就是明文 HTTP（ADR-0018 第 7 条），密钥在同一个网络上并不保密。
- 使用场景是宿主机与虚拟机之间的私有网络。

## 备选方案

1. 维持现状：共享密钥加防火墙规则。
2. 去掉密钥，靠防火墙规则、Host 头和 Origin 校验。
3. 密钥改为可选：默认不要，工程师可以在设置里要求。
4. 换成只在本机回环上监听，由宿主机经端口转发或 SSH 隧道连接。

## 决策

**选择方案 2**（项目负责人 2026-11-20）。

1. HTTP 请求不再校验 `Authorization`；不再有按来源的失败计数和锁定；Host 启动 HTTP 不再要求密钥文件存在。
2. 保留并作为仅有的防护：
   - Windows 防火墙入站规则 `EplanMcp.Vm.Http`，只放行工程师填写的宿主机 IPv4 到所选端口；
   - Host 头必须是绑定的地址和端口（防 DNS 重绑定，PRO-18）；
   - 有 `Origin` 头时必须在允许列表中。
3. 客户端配置只写 URL，不写请求头；“测试连接”不带密钥。旧配置里残留的密钥在替换和移除时仍然按密钥打码，不回显。
4. 新增不需要任何凭据的 `/health`，只返回服务名和版本。
5. 其余不变：只由工程师在 Workbench 中启动服务；一个服务对应一个 EPLAN；不加 TLS；审批仍只经独立窗口（[ADR-0011](0011-approval-out-of-band.md)），HTTP 客户端不能自己批准写入。

## 后果

- **好的**：连接步骤少了生成和分发密钥；不支持自定义请求头的客户端可以连接；客户端配置文件里不再有明文密钥。
- **坏的或要付出的代价**：
  - **防火墙规则成了唯一的访问控制。** 规则不存在、被别的软件或策略改掉、Windows 防火墙被关闭、或者服务绑定在规则没有覆盖的网卡上时，同一网络上的任何程序都能调用全部工具。此前这种情况下还有密钥挡着。
  - **宿主机上的任何程序都算“被放行”。** 规则按来源 IP 放行，分不出是工程师的 AI 客户端还是宿主机上的别的进程。浏览器里的网页受 Host 头和 Origin 校验限制；非浏览器程序不受限制。
  - 来源 IP 在同一个二层网络上可以伪造；NAT 或共享网络模式下，虚拟机看到的“宿主机地址”可能代表不止一台机器。
  - 没有失败锁定之后，探测和滥用没有任何限速。
  - 与 [ADR-0061](0061-auto-allow-ordinary-writes.md) 叠加：如果同时打开“普通写入自动放行”，能连到端口的程序就能不经任何人确认地修改真实项目。
- **建议补上的措施**（按决定实现时还没有的，由项目负责人取舍）：
  1. **启动 HTTP 前检查规则**：`EplanMcp.Vm.Http` 不存在、被禁用、放行范围不是单个地址、或 Windows 防火墙在该网络配置文件上关闭时，拒绝监听并说明原因；运行中定期复查，不满足时停止服务。
  2. Host 自己再校验一次来源地址等于配置的宿主机 IPv4（不依赖防火墙），不相符回 403。
  3. `doctor` 和 Workbench 状态页把“防火墙规则有效”列为虚拟机 HTTP 的必要条件，而不是参考信息。
  4. 虚拟机 HTTP 运行时，如果 `writesOutsideScratch` 是 `allow`，在 Workbench 给出明显提示，或不允许两者同时打开。
  5. `/health` 不返回版本号以外的任何信息（现在是这样，写成约束）。
- **后续行动**：更新 ADR-0018 的状态说明、`docs/standards/security.md` 的 TB7、入门文档的虚拟机部署一节（中英文及技能副本）、发布说明的支持矩阵（“自定义请求头”的要求去掉，Claude 桌面版的限制重新核对）；`HttpSecurityTests`、`HttpEndToEndTests` 改为新的行为；删除或标注不再使用的 `vm-key` 命令和 `VmKey`。跨机器的实机连接和经 UAC 建规则至今没有实测过（ADR-0018 的遗留项），去掉密钥后这项验证更有必要。

## 各方案利弊

### 方案 1（现状）
- 优点：两层防护互不依赖；密钥不依赖机器上的环境设置。
- 缺点：分发密钥麻烦；配置文件里有明文密钥；部分客户端不能用。

### 方案 2（去掉密钥）
- 优点、缺点：见“后果”。

### 方案 3（密钥可选）
- 优点：默认简单，需要的人仍有第二层。
- 缺点：两种模式都要维护和测试；界面上多一个要解释的开关。

### 方案 4（回环加隧道）
- 优点：服务完全不暴露在网络上。
- 缺点：工程师要自己配置端口转发或 SSH，对多数人太重（ADR-0018 当时已否掉类似方案）。
