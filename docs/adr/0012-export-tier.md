# ADR-0012：导出工具按 Read 级处理，注解 `readOnlyHint: false`，文件只写进 Host 新建的导出目录

| 决策人 | 项目负责人 |
| 门的类型 | 双向门（1.0 发布前） |

## 背景与问题
[M4 设计](../design/2026-10-20-m4-workflows.md)第一批有三个导出工具：`eplan_export_image`、`eplan_export_pdf`、`eplan_export_dxf`。它们不改项目的设计数据（S11，api-notes A16），但会在磁盘上新建文件。

[ADR-0005](0005-safety-model.md) 第 1 节规定级别与 MCP 注解一一对应（Read → `readOnlyHint: true`），CI 检查二者一致。导出放进哪一级都不合适：
- 按 Read，`readOnlyHint: true` 不准确：MCP 规范中它的意思是"不改变环境"，客户端可能据此不经询问就允许调用；
- 按 Write，真实项目上每次导出都要审批，可是导出并不改项目。

M4 设计 Q2 已按建议决定：采用 Read 级加 `readOnlyHint: false`，并另写本 ADR。改变 ADR-0005 的对应规则属于安全模型，是 L3。

## 决策驱动因素
- 注解要如实描述工具的行为，客户端会据此决定是否询问用户。
- 审批要留给改变项目的操作。审批太多，工程师会养成不看就批准的习惯。
- 导出的文件不能成为写任意位置的途径（威胁模型 T16 的同类问题）。

## 备选方案
1. **Write 级**：真实项目上每次导出都审批。
2. **Read 级，`readOnlyHint: true`**：不审批，注解不准确。
3. **Read 级，`readOnlyHint: false`、`destructiveHint: false`、`idempotentHint: false`**：不审批，注解如实说明"会写文件"，同时严格限制写到哪里。

## 决策
**选择方案 3。**

1. **级别与注解**：
   - ADR-0005 的对应规则补充一条：Read 级工具如果会在项目之外新建文件（目前只有导出），`readOnlyHint` 为 false，`destructiveHint` 为 false；
   - 每次调用都新建文件，所以 `idempotentHint` 为 false；
   - 工具规格中写明"写文件"。CI 的一致性检查按这条规则更新。
2. **位置**（M4 设计 4.4，新增威胁 T17 和要求 SEC-20）：
   - 导出只写进 Host 每次新建的空目录 `<数据根目录>\exports\<项目名>\<UTC 时间>-<随机后缀>\`；
   - 参数中没有目录，只有 PDF 可以给出文件名：不能含路径分隔符、驱动器号和 `..`；
   - Host 按 SEC-19 的规则确认目录在导出根目录之下、每一级都不是链接或联接点；
   - 导出后递归核对每个文件都在这个目录之下、不是链接；
   - 失败或取消时删除这个目录；
   - 从不覆盖已有文件。
3. **前提**：导出不改动项目的设计数据。S11 已证实（api-notes A16）：PDF、DXF 导出只改写项目的 `User.eod` / `User.eox`，这是 EPLAN 按用户保存的项目数据，任何 action 都会改写它（A11），不算修改设计数据；文件只出现在给定目录中，但 DXF 方案会在目录下建子目录。以后发现某种导出改动了设计数据，该工具按 Write 级处理，需要审批。
4. **不变的部分**：Write、Destructive、Code 的定义和策略；审批只针对改变项目的操作。

## 后果
- **好的**：
  - 工程师可以随时让 AI 导出图纸查看，不用每次审批；
  - 注解如实，客户端可以对"会写文件"的工具另行提示；
  - 导出文件的位置可以预测，便于清理和审计。
- **坏的或要付出的代价**：
  - ADR-0005"级别与注解一一对应"多了一条例外，CI 检查和工具设计规范第 8 节都要相应修改；
  - 导出目录不会自动清理，`doctor` 报告占用的空间（M4 设计 Q8）。
- **后续行动**：
  - 威胁模型加入 T17（导出写到允许的目录之外、覆盖已有文件、写到 UNC 共享）和 SEC-20；
  - 工具设计规范第 8 节的表格加上这条规则；
  - CI 的注解一致性检查按规则更新；
  - 本 ADR 接受之前，导出工具不合并（M4 设计 Q2）。
