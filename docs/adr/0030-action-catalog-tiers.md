# ADR-0030：EPLAN action 分三级开放：已验证条目照旧、全部 action 只读可查、未验证 action 只在 scratch 中逐次审批后执行

| 项 | 内容 |
|---|---|
| 状态 | Proposed |
| 日期 | 2026-10-30 |
| 决策人 | 项目负责人 |
| 门的类型 | 单向门：未验证执行一旦发布，工作流和技能会依赖它；收紧要按工具契约变更处理 |
| 影响 | 放宽 [ADR-0021](0021-action-run-whitelist.md) 门的类型一栏所说"未经验证的条目"的限制（本 ADR 即其要求的新 ADR）；不改变 ADR-0021 的白名单条目、级别和流水线；涉及 [ADR-0005](0005-safety-model.md) 的审批模型 |
| 相关依据 | [M10 设计](../design/2026-10-30-m10-capability-expansion.md) |

## 背景与问题

EPLAN 界面中约有 1150 个 action（ADR-0021 背景），其中约 1050 个只是界面按钮，没有官方说明。项目负责人 2026-10-30 要求"1050 个 action 也需要全部加入进去"，并同意按"三级"方案实现。

ADR-0021 只允许执行随产品发布、经实机验证的白名单条目。很多未验证的 action 会弹对话框、改设置、删数据或关闭项目（api-notes A25 的部件清单导出关闭了全部项目），直接开放会绕开"写操作可回滚、可撤销、可审计"的底线。

## 决策驱动因素
- 负责人要求覆盖全部 action；
- 不凭文档或名称假设 action 的行为（CLAUDE.md "写代码之前先读"）；
- 安全默认值不可悄悄放宽；模型给的参数一律不可信（security.md TB1）；
- 不分发 EPLAN 的安装文件（CLAUDE.md 硬性规则 4 的精神：不提交第三方受保护内容）。

## 备选方案
1. 维持 ADR-0021：只开放已验证条目，其余逐个 spike 后加入。
2. 全部 1050 个都按 Destructive 级开放，在任何项目中逐次审批。
3. **分三级**：A 级已验证条目（ADR-0021 不变）；B 级全部 action 只读目录；C 级未验证 action 只在 scratch 项目中、逐次审批后执行，并配批量自动验证，把验证通过的 action 升为 A 级。

## 决策
选择方案 3。

### A 级：已验证（不变）
ADR-0021 的白名单和流水线原样保留，`eplan_action_run` 的行为不变。

### B 级：只读目录
- 新增只读工具（名称按工具设计规范定，例如 `eplan_action_catalog_search` / `eplan_action_catalog_get`），分页列出和搜索全部 action：名称、所在菜单或功能区位置、界面文字、已知参数、所属级别（A/C）、验证记录。
- 目录**运行时从本机 EPLAN 安装中读取**（`MFTools.xml` 及同类文件），只在本机缓存；仓库不提交 EPLAN 的文件或从中整理出的完整清单。
- 读取失败或版本不同时返回缺口，不猜测。

### C 级：未验证执行
- 新增独立工具（例如 `eplan_action_try`），不并入 `eplan_action_run`，避免模型把已验证与未验证混为一谈。
- **只作用于 scratch 根目录下的项目**；scratch 之外一律 `POLICY_DENIED`，不提供审批绕过。
- **每次调用都审批**，审批内容显示 action 名、参数原文、目标项目、"未验证"标记和已知风险提示；不允许"本次会话不再询问"。
- 参数按名称和长度做基本校验（无路径穿越、无凭据、无执行另一个 action 的参数）；拒绝 ADR-0021 第 1 节列出的不能成为条目的类别（脚本、安装器、凭据、发布到外部服务）。
- 执行前后自动做业务快照和文件指纹对比，结果如实列出变化；有执行时限，超时或出现模态对话框时报告 `unknown` 并暂停后续写入（ADR-0010）。
- 全部记入审计，标记为未验证执行。
- 默认关闭，由 `config.json` 显式开启（与 ADR-0021 的开关一致）。

### 批量自动验证
- 提供维护者工具：在 scratch 副本上逐个试跑 action，记录是否弹窗、耗时、改动的文件与设置、能否被 `SafetyPoint` 回滚、能否一步撤销，生成报告；结论写进 api-notes。
- 通过验证的 action 按 ADR-0021 第 2 节的流程加入 A 级白名单（一个 PR 若干条目，引用验证记录）。

## 后果
- **好的**：全部 action 可查可用；风险集中在 scratch，由人逐次把关；验证工作可批量推进，A 级持续扩大。
- **坏的或要付出的代价**：C 级结果只能比较前后快照，做不到任务工具那样逐项核对；逐次审批对批量使用不便；本机 `MFTools.xml` 的格式随版本变化，需要维护读取器。
- **后续行动**：先做 B 级和批量验证工具，再做 C 级；C 级发布前补 Large 测试（模态对话框、超时、scratch 外拒绝、审计标记）；security.md 增加 C 级的威胁说明。
