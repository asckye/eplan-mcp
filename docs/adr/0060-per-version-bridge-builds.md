## 背景与问题

ADR-0009 决定按 EPLAN 2026 的 API 程序集构建一份 net481 插件，在 2024–2027 上通用。它的依据之一是“插件用到的 API 在 2022–2027 的文档中都存在，签名相同”。这一条已经不成立：

1. **用户报告（#664，EPLAN 2025.0.3）**：读页面图形和所有要读页面的写入计划抛 `MissingMethodException`。原因是 `PathMap.SubstitutePath(String, String)` 从 2026 才有（B17）。运行时编译一个方法时要解析它引用的全部成员，缺一个，整个方法都不能用。
2. **报告人按 2025.0.3 的程序集编译 `6d14f7ec`**：2,781 处编译错误。其中 2,778 处在生成的 `ApiTryDispatch.g.cs`，3 处在手写代码（上面那个、`PropertyPlacement.GetBoundingBox(Boolean)`（B18）、`MDPartsDatabase.ImportMode.ReplaceAndAppend`）。另有一处不报错的：`InstallationSpace.Connection3Ds` 在 2025 不存在，同一行代码绑定到基类的同名成员，结果是空的。
3. **规模**：报告人用本仓库的提取工具生成了 2025 的 API 目录，与 `catalog/eplan-2026.0.3` 对比，2026 独有的标识 3,187 个，插件用到其中 2,374 个（除 4 个外都只在生成的代码里）。这些数字是报告人的，我们没有 2025 的程序集，未复核；其中两个成员按官方 API 文档核对过。

现在的做法是每发现一个缺失成员就加一处运行时回退（`EplanPaths`、`EplanTextBounds`）。它能修已知的那一个，但下一个只有用户撞上才知道，静默绑定到别的成员那一类根本不会报错。

ADR-0009 当时参考过 TIA_Portal_Openness_MCP，认为它“每个版本各编译一份”的原因（进程外 API、每版本强名称不同）在 EPLAN 上不存在，所以不需要。2026-11-20 重新看了那个项目的现状：它对 8 个版本用同一套源码各编译一次，版本差异只允许写在一张集中的功能符号表上并有检查工具，各版本的 SDK 只放在开发机本地，一个发布包带全部版本。它这样做的收益（缺失成员在编译期暴露）与 API 是否进程外无关，对 EPLAN 同样成立。

## 决策驱动因素

- 数据完整性第一：一个成员在某个版本上不存在或含义不同，应当在编译时发现，而不是在工程师的项目上发现。
- “支持”要有证据：编译通过只证明接口对得上，不等于行为正确；行为仍要实机验证（ADR-0009 前提 2 不变）。
- 开发机现在只有 EPLAN 2026。没有某个版本的 API 程序集，就编不出那个版本的插件。
- EPLAN 的程序集是授权软件：不入库、不随包分发、不向第三方索取（[ADR-0007](0007-licensing-and-distribution.md)）。
- Host、工具契约和进程模型不变（[ADR-0002](0002-host-bridge-process-model.md)）。
- 版本差异会越积越多；TIA 项目记录过约 30 处“API 并不要求”的版本差异，后来专门立规则清理。

## 备选方案

1. **维持一份按 2026 的构建，逐个成员加运行时回退**（现状）。
2. **一份按最低支持版本（2024）的构建**，新版本才有的成员一律用反射。
3. **每个支持的版本各构建一份**：同一套源码，按该版本自己的 API 程序集编译，版本差异用编译符号表达；每个 EPLAN 安装注册与它对应的那一份。
4. **只为 2026 和“其他版本”各一份**（两份），其他版本那份按 2024 编译。

## 决策

**选择方案 3**（项目负责人 2026-11-20 同意），按下面的规则实施。

1. **构建**：`EplanVersion`（年份）决定引用哪个安装的 `Bin` 目录和输出目录 `bin\<配置>\net481\eplan<年份>\`；不传参数时仍是 2026，产物与现在相同。现有的程序集身份检查（文件版本的主版本号必须等于 `EplanVersion`）保留。
2. **版本差异只写在一个地方登记过的符号上**：集中一个文件定义符号和各自适用的版本范围；源码里的版本条件编译只许用这些符号，加一项检查拒绝别的写法。优先用“功能”命名（例如“有按项目解析路径的重载”），不是到处写年份比较。版本之间不是 API 要求的差异不允许存在。
3. **生成的代码按各版本自己的 API 目录各生成一份**（`catalog/eplan-<版本>/`）。`eplan_api_try` 在某个版本上没有的成员，返回 `CAPABILITY_MISSING`，不抛 `MissingMethodException`。`ApiTryCatalog`（Contracts，不引用 EPLAN）仍是一份，记录每个条目存在于哪些版本。
4. **某个版本做不到的功能明确拒绝**：在调用原生 API 之前返回 `CAPABILITY_MISSING` 并说明需要哪个版本；不静默降级，不绑定到含义不同的成员。
5. **支持矩阵分三档，分开写**：已实机验证（现在只有 2026）；已按该版本编译、未实机验证；未涉及。只有第一档算“支持”。握手和 `doctor` 报告插件是按哪个版本构建的、与正在运行的 EPLAN 是否一致（ADR-0009 前提 3 的延伸）；不一致时拒绝写入。
6. **发布**：一个 ZIP，`bridge\net481\eplan<年份>\` 每个已构建的版本一个目录；注册时按每个 EPLAN 安装的版本选对应目录，没有对应构建的版本不注册并说明原因。发布包只带维护者自己编译并跑过离线测试的版本；某个版本的构建若只由贡献者验证过，不进发布包，直到维护者机器上有那个版本。
7. **各版本的 API 程序集只放在构建机本地**，来源是官方安装；API 目录（我们自己格式的成员清单）可以入库，和现有的 2026 目录一样。

理由：

- 缺失成员和签名变化在编译期全部暴露，静默绑定错误也能靠按版本的目录对比找出来；现状每个只能等用户报告。
- Host 与版本无关、插件在 EPLAN 进程内，这个结构已经和“每版本一份适配层”对得上，不需要改进程模型和工具契约。
- 方案 2 要把生成代码里的两千多处直接调用改成反射，失去生成器本来提供的编译期检查，并且永远落在最低版本的能力上。
- 方案 4 只比方案 3 少几份构建，却把 2024、2025、2027 之间的差异又藏回运行时。

## 后果

- **好的**：2025 等版本上的缺失成员不再靠用户发现；支持矩阵的“支持”有编译证据作为下限；`EplanPaths`、`EplanTextBounds` 这类运行时回退可以换成编译期分支。
- **坏的或要付出的代价**：
  - 构建机要装每个要发布的版本（至少要有它的 `Bin` 目录）。现在只有 2026；在装上之前，发布包仍然只带 2026 那份。
  - 构建、关卡、打包、离线 Large 测试的时间随版本数增加；发布检查清单（文件清单、哈希、SBOM）要按多目录改。
  - GitHub CI 没有 EPLAN，本来就不编译插件，这一点不变；按版本的编译只在本地关卡里把关。
  - 每个版本的 API 目录要随 EPLAN 的补丁版本更新；符号表每次改动都要审。
  - 已安装用户的插件路径会变；注册要能从旧的单一路径迁移过来。
- **后续行动**（接受后，按顺序，每步单独一个变更集）：
  1. 提取并入库 2025 的 API 目录；对比 2026，列出插件用到而 2025 没有的成员，写入 api-notes。
  2. 构建参数、符号表和检查；默认构建的产物不变。
  3. 生成器按目录生成；`ApiTryCatalog` 记录版本范围。
  4. 手写代码的四处差异改为编译期分支；补 3D 连接那处静默错误。
  5. 打包、注册、`doctor`、握手的版本一致性检查；发布流程文档。
  6. 2025 的实机验证（ADR-0009 前提 2 的清单），结果入验收台账；通过后才把 2025 写进“已实机验证”。
  7. 更新 ADR-0009（构建方式指向本 ADR）、架构文档、`docs/eplan/eplan-versions.md`、README 的支持矩阵。
- **接受前要确认的事**：项目负责人能否提供 EPLAN 2025 的安装（编译只需要文件，实机验证需要能启动它的授权且含 API 扩展）；外部贡献（#664 报告人的分支）按第 1–4 步拆开提交，合并前在 2026 上跑全部 Large。

## 各方案利弊

### 方案 1（现状）
- 优点：一份构建，发布最简单。
- 缺点：缺失成员逐个由用户发现；静默绑定错误发现不了；`eplan_api_try` 的生成代码在 2026 以外整体不能用。

### 方案 2（按最低版本构建加反射）
- 优点：一份构建。
- 缺点：失去编译期检查；新版本的能力都要手写反射；最低版本的程序集仍然必须有。

### 方案 3（每版本一份）
- 优点：见“理由”。
- 缺点：见“代价”。

### 方案 4（两份）
- 优点：构建数量少。
- 缺点：2024、2025、2027 之间的差异仍在运行时才暴露。
