# ADR-0009：支持 EPLAN 2024–2027，用一份 net481 插件构建；2022、2023 暂不支持

## 背景与问题
项目负责人问：EPLAN 2022–2027 能否都支持？[ADR-0004](0004-runtimes-and-target-frameworks.md) 目前只承诺 2026：插件以 net481 为目标；2027 预计可用，留到 M6 验证；2024、2025 待调查；没有涉及 2022、2023。"支持哪些 EPLAN 版本"属于 L3 决策（CLAUDE.md 硬性规则 3）。

2026-10-19 逐个版本核对了 2022–2027 的官方 API 帮助和软件要求页面，完整结果见 [EPLAN 各版本的 API 兼容性](../eplan/eplan-versions.md)。要点如下：

1. **目标框架**：2.9 到 2023 的 API 是 .NET Framework **4.7.2**，2024 起是 **4.8.1**；2027 仍要求 4.8.1，同时新增并行的 .NET 8 API，没有找到 .NET Framework API 被废弃的说明。
2. **官方兼容规则**："API add-ins compiled with the .NET Framework 4.8.1 are only executable in the Eplan Platform Version 2024 and higher"；插件不需要重新编译，"remain executable in the Eplan Platform version in which they were created and in all newer versions"（2024 软件要求页）。
3. **插件用到的 API**：类型和成员在 2022–2027 的文档中都存在，签名相同。**唯一的例外是 `EplanMainThreadDispatcher`**：整个 `Base.Internal` 命名空间在 2022–2024 的文档中都没有，2025 起才出现。插件现在在 `OnInitGui` 中调用它。
4. **Newtonsoft.Json**：插件运行时使用 EPLAN 自带的 Newtonsoft.Json 13。官方文档没有写各版本自带的是哪个版本，只有 2026（13.0.3）是本机确认过的。
5. **签名与授权**：签名流程逐年变化（2022–2023 用 File Exchange，2024 起用 EPLAN Cloud 签名服务，2026 起改为自动签名）；2026 起，直接或间接使用 EPLAN API 的所有 DLL 和 EXE 都要签名。这只影响走运行时授权的分发方式（[ADR-0007](0007-licensing-and-distribution.md)）。
6. **2022 的平台**：官方操作系统兼容表只在已停止服务的 Windows 版本下列出 2022。

另外参考了项目负责人的 TIA_Portal_Openness_MCP 项目。它为 8 个 TIA 版本各编译一份、每个会话起一个对应版本的进程，原因是 TIA Openness 是进程外 API，每个版本的程序集强名称都不同。EplanMcp 的插件运行在 EPLAN 进程内，Host 与 EPLAN 版本无关（[ADR-0002](0002-host-bridge-process-model.md)），不需要这套机制。2026 的 EPLAN API 程序集版本固定为 1.0.0.0（api-notes B1），这让"一份构建支持多个版本"有可能成立。

## 决策驱动因素
- 数据完整性第一：每个支持的版本，都要把 2026 上验证过的行为（回滚与撤销、LockingStep、模态对话框、消息集合）重新实测一遍，不能只靠文档。
- 开发机只有 2026；没有安装和授权的版本无法测试，说"支持"就要有人能装上它跑一遍。
- 构建、安装包和工具契约越少越好。
- 中国工程师常用的版本分布不清楚；老项目可能还留在旧版本上。

## 备选方案
1. **只支持 2026**（维持现状）。
2. **一份 net481 构建，支持 2024–2027**；2022、2023 暂不支持，有明确需求时再按方案 4 补上。
3. **一份 net472 构建，支持 2022–2027**：针对 2022 或 2023 的 API 程序集编译，依靠官方的向前兼容规则在新版本中运行。
4. **两份构建**：net472（2022–2023）和 net481（2024–2027）。

## 决策
**建议选择方案 2**，同时满足下面三个前提：

1. **去掉对 `EplanMainThreadDispatcher` 的硬依赖**：在 `OnInitGui`（主线程）中取 `Dispatcher.CurrentDispatcher`，主线程断言改用 `Dispatcher.CheckAccess()`。2026 上两者是同一个对象（api-notes A9），这个改动对 2026 没有影响。
2. **按版本做实机验证（spike S7）**：在 2024、2025、2027 的实机或虚拟机上，用 scratch 项目核对：
   - 插件能否加载，程序集标识（版本号、强名称），Bin 中 Newtonsoft.Json 的版本；
   - 2026 上验证过的行为是否一致：api-notes A7、A9、A10、A11 中的回滚与撤销、LockingStep、模态对话框、`SysMessagesCollection`、按页过滤连接、`User.eod` 改写；
   - M2 的 Large 测试全部通过。

   验证通过的版本才写进支持矩阵；结果写入 api-notes，逐版本记录在验收台账中。
3. **版本信息透明**：`doctor` 报告本机的 EPLAN 版本，以及它是否在支持范围内；握手结果带上插件的构建目标；连上不在支持范围内的 EPLAN 时，`eplan_session_status` 明确说明，而不是在某个工具调用时莫名失败。

理由：
- 方案 2 只有一份构建，契约和安装包也只有一份，覆盖面比现状大一倍。
- 2024–2027 用的是同一个 .NET Framework 版本，官方规则明确支持；我们用到的 API 在这几个版本中签名相同，唯一的障碍（调度器）可以用对 2026 无影响的方式去掉。
- 2022、2023 需要按 4.7.2 针对它们自己的 API 程序集编译，必须有装着这两个版本的机器才能构建和测试；2022 只在已停止服务的 Windows 上受支持。现在投入的成本高、收益不确定。
- 方案 3 用一份构建覆盖六个版本，代价是必须针对 2022 编译，并且永远不能使用 2022 之后新增的 API；方案 4 要维护两份构建。它们留到有工程师确实需要 2022、2023 时再选，那时只需新写一份 ADR 扩大范围，现有决定不必推翻。

## 后果
- **好的**：一份构建覆盖四个版本；Host 和工具契约不变；2027 继续用 .NET Framework API，不需要开发 .NET 8 版本的插件，与 ADR-0004 一致。
- **坏的或要付出的代价**：
  - 需要 2024、2025、2027 的安装和授权来做验证；在验证之前，支持矩阵只能写"预计可用"。
  - 使用 2022、2023 的工程师用不了，要么升级 EPLAN，要么等后续 ADR。
  - 将来如果想用 2025 及以后才有的 API，就要在运行时探测，并在握手中声明能力。
- **后续行动**：
  - 前提 1（调度器）在本 ADR 接受后单独一个 PR 实现。
  - spike S7 排进 M2 收尾到 M3 之间；需要的 EPLAN 安装由项目负责人确认来源。
  - 更新 ADR-0004（支持矩阵指向本 ADR）、架构文档第 2 节和第 11 节（M6 改为"2024、2025、2027 验证"）、README 的环境要求。
  - 按 TIA 项目的经验，构建时校验插件引用的 EPLAN 程序集身份，防止误用其他版本的 Bin 目录编译。
