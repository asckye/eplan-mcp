## 背景与问题

ADR-0005 的判定表里，Write 级别的工具在 scratch 项目中自动允许，在 scratch 根目录之外（工程师的真实项目）每次都要审批；`config.json` 的 `writesOutsideScratch` 只有 `deny` 和 `approve`（默认）两个值。

Workbench 重新设计时（2026-11-20），项目负责人决定在设置页提供“普通写入是否需要确认”的开关：在真实项目上连续做大量可撤销的小改动时，逐个审批让工程师无法使用。

## 决策驱动因素

- 数据完整性仍是第一位：不可撤销或影响面大的写入不能因为这个开关而失去审批。
- 开关必须由工程师本人在本机打开，AI 客户端不能自己打开。
- 当前处于哪种模式要随时看得见。

## 备选方案

1. 维持现状：scratch 之外的 Write 每次审批。
2. `writesOutsideScratch` 增加 `allow`：普通写入不再审批，其余不变。
3. 按项目或按会话的临时放行（例如“本次会话 30 分钟内不再询问”）。
4. 按工具放行（工程师勾选哪些工具免审批）。

## 决策

**选择方案 2**（项目负责人 2026-11-20）。

1. `writesOutsideScratch` 的取值为 `deny`、`approve`（默认，不变）、`allow`。
2. `allow` 时，策略引擎对 **Write 级别、不涉及主数据** 的写入返回“允许”，不论项目是否在 scratch 根目录中。
3. 以下仍然每次审批，`allow` 不影响它们：
   - Destructive 级别（删除、整个项目重编号、覆盖式导入等），执行前照常自动备份；
   - 涉及系统主数据的写入（[ADR-0019](0019-master-data-writes.md)）；
   - 未验证的写入（`eplan_api_try`、`eplan_action_try`）；
   - 解除写入暂停（[ADR-0010](0010-write-outcomes.md)）。
4. Code 级别仍然默认禁用。`deny` 的含义不变。
5. 开关在 Workbench 的设置页、状态栏和审批页，写入本机的 `config.json`；三处都显示当前模式，`doctor` 报告当前取值。
6. **是否放行只由 Host 判断，并且每次写入时读 `config.json` 的当前值**，不用启动时的值。工程师把审批重新打开后，下一次写入就会询问，不必重启正在运行的 Host。只有这一个值跟随文件；scratch 根目录等其余配置仍是启动时的。文件读不了或内容无效时一律不放行：按“需要审批”处理，启动时是 `deny` 的保持 `deny`。
7. **Workbench 不替工程师回答审批。** Host 仍然发来的每个请求都显示在队列里，包括 `allow` 下的未验证写入。
8. `deny` 不是开关的一个状态：配置为 `deny` 时界面如实显示“禁止”，开关不可用，只有编辑文件才能改。保存失败时什么都不变，界面显示文件里的值。
9. 组合计划（`eplan_plan_apply`）按其中级别最高的步骤判定：全部是 Write 级别的计划在 `allow` 下同样不询问。
10. 写入的其余保护不变：事务与撤销、写后读回、项目状态指纹、审计记录。`allow` 下每次写入照常进审计：`execution_started` 记录里 `policy` 为 `Allow`，并且没有对应的 `approval` 记录，与工程师批准过的写入可以区分。

## 不变的部分

- 开发规范里“AI 代理只在 scratch 项目上做写操作”（CLAUDE.md 硬性规则 1，AI-10）约束的是在本仓库里工作的开发代理和测试，不是产品的运行策略；它不变。Large 测试和评测仍然只写 scratch。
- 默认值不变：新安装和没有改过配置的工程师，行为与现在相同。

## 后果

- **好的**：在真实项目上做大量可撤销的小改动时不再被审批打断；一个开关，含义容易讲清楚。
- **坏的或要付出的代价**：
  - `allow` 打开后，AI 对真实项目的普通写入没有人逐个看。错误只能靠撤销、写后读回的警告和事后检查发现；一次会话里的多次写入，撤销要逐步进行。
  - “普通写入”的范围由工具的级别标定决定：哪个工具标成 Write 而不是 Destructive，直接决定它是否免审批。以后新增或调整工具级别时，要把这一点当作审查项。
  - `config.json` 是本机的普通文件。能改这个文件的程序就能打开这个开关，而且因为 Host 每次写入都读它，改动立即生效；AI 客户端如果有本机文件写入能力，理论上也能改。
- **建议补上的措施**（按决定实现时还没有的，由项目负责人取舍）：
  1. `eplan_session_status` 里明确报告当前是 `allow`，让 AI 客户端和工程师都看得到。
  2. Workbench 关闭审批时要求一次确认，并说明哪些写入仍会询问；现在状态栏上点一下就切换。
  3. 组合计划在 `allow` 下是否仍应询问一次：一个计划可以有几十步，现在按步骤级别判定，不询问。
  4. 评测里加一组用例：`allow` 下 Destructive、主数据、未验证写入仍然询问。
- **后续行动**：更新 ADR-0005 的“后续修订”、架构文档的安全一节、入门文档的配置说明、`docs/standards/security.md` 的威胁模型（没有人在环的写入路径）；`PolicyEngineTests` 覆盖新的一行判定。

## 各方案利弊

### 方案 1（现状）
- 优点：每次写入都有人确认。
- 缺点：真实项目上的批量小改动实际不可用。

### 方案 2（`allow`）
- 优点、缺点：见“后果”。

### 方案 3（限时放行）
- 优点：放行会自动结束，忘记关的风险小。
- 缺点：要有计时和会话的概念，界面和状态都更复杂。

### 方案 4（按工具放行）
- 优点：粒度细。
- 缺点：一百多个工具，工程师难以逐个判断；配置容易出错。
