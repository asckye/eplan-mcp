# ADR-0047：采用按种类组织的工程包作为插件，从内置库和登记的本地或共享目录库安装，按全局、项目、柜体作用域启用

## 背景与问题
负责人 2026-11-02 要求把国际标准提前做成插件放进 MCP（"标准插件库"），其他能力也按插件库组织，并能在 Workbench 中添加和加载。

现状：
- 有工程包（`.eplanpack`，ADR-0024：只含数据、安装前校验、安装后不可变），也有项目和柜体两级的版本锁定（M6 4.1.5）。
- 没有"库"的概念，只能手工导入单个包文件。
- 包没有种类，工具也不会按已启用的包取默认值。例如客户页重绘要用 SPECIAL `BPIN`/`BPOUT` 作中断点、`TDEF` 作端子排定义，这类约定目前只能写死在清单里。
- 没有全局启用。

## 决策驱动因素
- 插件只能是数据，不能执行（ADR-0024 第 1 节）；需要代码的能力仍走 ADR-0025/0031。
- 由工程师决定信任谁：外来的插件必须经人确认才能安装。
- 每次调用都能说清用了哪个插件的哪个版本（M6 的溯源）。
- 不收录、不分发标准原文（M12 非目标）：标准插件只放可检查的规则参数、条款号、代码映射和默认选择这类事实。
- 与现有的包锁定、`eplan_context_get` 溯源兼容，不另起一套。

## 备选方案
1. 维持现状：只能手工导入 `.eplanpack`，没有种类、库和全局启用。
2. **插件 = 带种类的工程包；从内置库和登记的本地或共享目录库安装；按全局、项目、柜体三级启用。**
3. 允许插件携带代码，安装后由 Host 加载。
4. 建中心化的网络插件商店，签名强制。

## 决策
选择方案 2。

### 1. 插件就是工程包
- `pack.json` 增加 `kind`：`standard`、`parts`、`symbols`（符号库与宏）、`templates`（基础项目、表格、图框、报表模板）、`company`。
- `pack.json` 增加 `provides`：列出它提供的默认项键，例如 `defaults.interruptionSymbol`、`defaults.stripDefinitionSymbol`、`rules`、`wireColours`、`designationLetters`。
- 依赖沿用现有的 `dependencies`。
- 仍只含数据，容器校验、不可变和存放位置不变（ADR-0024 第 1、2、5 节）。

### 2. 插件库
- 插件库是一个目录，根下有 `library.json` 索引，列出每个插件的 ID、版本、种类、摘要、文件名和简短说明。
- 来源有三种：
  - **内置库** `builtin`：随发行版附带，按发行清单核对哈希，安装不需要确认。首批是 IEC、GB、NFPA 标准插件。
  - **本地库**：数据根目录下的 `plugin-libraries\<名称>\`。
  - **共享目录库**：`config.json` 的 `pluginLibraries` 中登记的根目录，可以是 UNC 路径。只读，与 ADR-0024 第 6 节的 `packSources` 规则相同。
- 网络源和强制签名不在本 ADR 范围内，需要时另写 ADR。
- 库索引中的文字是数据（ADR-0024 第 7 节），不能据此执行任何操作。

### 3. 安装确认
- 内置库以外的插件，每次安装都经审批渠道确认一次（ADR-0024 第 4 节），确认内容加上库名称和来源路径。
- 更新也是一次新的安装，同样需要确认。
- 安装、更新、卸载、启用、停用都写审计（沿用 `pack_change`）。

### 4. 作用域启用与解析
- 三级作用域：
  - **全局**：`config.json` 中的 `enabledPlugins`；
  - **项目**：项目绑定中的锁；
  - **柜体**：柜体配置链中的锁。
  - 后两级都是 M6 现有的机制。
- 解析顺序：柜体覆盖项目，项目覆盖全局。同一作用域内，按列出的顺序后者覆盖前者。
- 同一默认项被多个插件提供时，结果在 `eplan_context_get` 的溯源中列出生效的插件和被覆盖的插件。
- 启用和停用改变的是本地配置或绑定，不改 EPLAN 项目；改项目和柜体的锁仍要工程师确认（M6）。

### 5. 工具如何使用插件
- 绘图、审查、建项目等工具从当前作用域已启用的插件读取默认值。工具参数中显式给出的值优先于插件。
- 写入仍走审批、事务和撤销，ADR-0005/0010 不变。
- 结果在 `metadata` 中记录用到的插件，格式为 `插件 ID@版本`。

### 6. Workbench
- 新增"插件"页：库、浏览、安装与更新、启用到作用域、冲突与依赖。
- 页面上的操作都调用同一套后端操作，与 MCP 工具共用审计，不另开写入通道。

## 后果
- **好的**：
  - 标准约定、公司规则、部件和模板可以分开发布、按项目选用；
  - 工程师在界面上就能看到每个项目用了哪些插件；
  - 第三方插件不会在无人确认时进入系统；
  - 和现有包机制兼容，迁移成本低。
- **坏的或要付出的代价**：
  - 多了一层解析和冲突处理，工具结果要带上插件溯源；
  - 共享目录库可能被他人改写：安装时校验摘要，安装后不可变，可以缓解；
  - 内置库免确认，依赖发行包本身可信，与程序本身同等。
- **后续行动**：
  1. 设计文档 `docs/design/2026-11-02-plugin-libraries.md`，分 P1–P3 实施；
  2. 安全文档补充库来源规则；
  3. Small 测试覆盖：索引解析、作用域覆盖顺序、确认流程、溯源。

## 各方案利弊
### 方案 1
- 优点：不用新增代码。
- 缺点：标准约定只能写在每个清单里，无法复用，也无法在界面上管理。
### 方案 3
- 优点：插件能力最强。
- 缺点：违反 ADR-0024 只含数据的原则；代码插件已有 ADR-0025/0031 的隔离方案，不应混入。
### 方案 4
- 优点：分发方便。
- 缺点：0.x 没有签名基础设施（ADR-0024 第 3 节），网络来源扩大攻击面；负责人已确认先做本地和共享目录。
