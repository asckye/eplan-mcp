# ADR-0051：发布包在开发机上打包，不经发布工作流

| 项 | 内容 |
|---|---|
| 状态 | Accepted |
| 日期 | 2026-11-05（负责人："本地打包，上传，不要用CI了"；"常规 CI 不用停"） |
| 决策人 | 项目负责人 |
| 门的类型 | 双向门：`release.yml` 保留，改回标签触发就能恢复 |

## 背景与问题
[ADR-0020](0020-no-self-hosted-runner.md) 之后，插件在开发机上按标签构建，其余部分由 `release.yml` 构建和打包。v0.5.0 发布时，负责人决定整个包都在本地打，上传到草稿。

## 决策驱动因素
- 负责人的决定，发布不依赖云端工作流。
- 产物结构和校验方式不能变，工程师下载到的 ZIP 和以前一样。
- 不装自托管 runner（ADR-0020 不变）。

## 备选方案
1. 继续用 `release.yml` 打包。
2. 新脚本 `eng/scripts/release-package.ps1` 照搬工作流的构建和打包步骤，在 `release-addin.ps1` 保留的标签 worktree 上运行；工作流只留手动触发。

## 决策
选择方案 2。发布前的本地关卡、冒烟测试和实机证据要求不变。main 的常规 CI 不变，打标签前仍要看它是否通过。

## 后果
- **好的**：发布不等云端，失败时能在本机直接查。
- **坏的或要付出的代价**：没有 GitHub 构建证明（provenance、SBOM attestation），它们要 GitHub Actions 的身份，所以附件从 8 个变成 6 个，`gh attestation verify` 不适用；校验靠 `SHA256SUMS.txt` 和逐文件清单。程序包的构建环境从干净的云端机器变成维护者的开发机，靠全新 worktree、锁定还原和构建后扫描本机路径来弥补。上传速度取决于本机网络：v0.5.0 的 146 MB ZIP 用了约一小时。
- **后续行动**：发布说明写明没有构建证明；v0.4.1 及更早版本的证明仍然有效。
