# ADR-0023：组合计划一次审批（带差异预览）、开始前备份一次、每步一个事务，计划级结果增加 `partially_committed`

## 背景与问题
[M6 设计](../design/2026-10-21-m6-engineering-packs.md) 4.8 把工程意图编译为有序的多步计划（例如新建页、插入模块、改属性、生成连接），由 `eplan_plan_apply` 执行。现有的写入流水线（`src/EplanMcp.Host/Safety/WritePipeline.cs`）一次工具调用只有一对 `*.plan`/`*.execute` 操作、一个 Bridge 事务、一次审批。直接套用会有几个问题：
- 每步审批一次，一个意图要点很多次，工程师容易不看就批准；
- 一个事务包住整个计划：长时间占住 EPLAN 主线程；按符号新建功能只能在 `Transaction` 中、不能在 `SafetyPoint` 中（api-notes A13）；EPLAN 在途中被结束时，事务中已做的修改照样留在项目里（A15，spike S8）；
- 每步一个事务时，后面的步骤失败，前面已经提交的步骤不会回滚，ADR-0010 的四个执行状态表达不了"做了一部分"（ADR-0010 否决 A4 的理由正是"一次调用一个 SafetyPoint 时不会出现部分完成"）。

这改变审批模型和写入结果的契约，属于 L3，只能提议。

## 决策驱动因素
- 数据完整性第一（[架构](../architecture/architecture.md) 1.3）：任何失败之后都要有可靠的退路，结果要说清楚。
- 审批针对具体的变更清单（ADR-0005 第 3 节），工程师批准的就是将要执行的，执行不能超出批准的范围。
- 安全默认值不悄悄放宽：Destructive 照样每次审批、先备份；真实项目照样按 `writesOutsideScratch`。
- EPLAN 主线程串行，工程师可能在执行期间同时操作。
- 对代理友好：一个字段说清楚项目处于什么状态，下一步做什么。

## 备选方案
- **审批**：A1 每步审批一次；**A2 整个计划审批一次，展示按步、按页分组的差异预览**；A3 Write 步骤一起审批，每个 Destructive 步骤再单独审批。
- **事务**：B1 整个计划一个 `SafetyPoint`；**B2 每步一个 `SafetyPoint` 和撤销步骤**。
- **备份**：C1 只有 Destructive 步骤才备份（现状）；**C2 每个计划开始前备份一次，Destructive 步骤另按 ADR-0013 备份**；C3 每步之前都备份。
- **结果**：D1 只报告各步的结果；**D2 计划级结果在四个值之外增加 `partially_committed`，各步仍是四个值**；D3 把"做了一部分"归为 `unknown`。

## 决策
选择 **A2 + B2 + C2 + D2**。

### 1. 审批
- 计划经策略判定（第 2 条）需要审批时，**整个计划只请求一次**，经 ADR-0011 的渠道（Workbench 优先，否则 EPLAN 内的对话框）。
- 展示：计划 ID、项目、柜、最高级别、备份位置；按步、按页分组的变更清单，Destructive 步骤醒目标出；由 Host 预测、执行时才由 Bridge 真实规划的步骤（设计 4.8.2）标明"按模式匹配"及允许的模式；"每步是一个单独的撤销步骤"。
- EPLAN 对话框显示每步的摘要和前 50 条变更，完整清单写在 `<数据根目录>\state\plans\<planId>\changes.txt`，对话框给出路径；Workbench 显示完整的差异。
- 绑定：（请求 ID，`planHash`，不依赖前面步骤的各步指纹的组合，参数摘要），只能用一次，期限同 ADR-0011。

### 2. 策略
- 计划的级别是各步的最高级别。只有 Write 步骤、目标在 scratch 中：自动允许（ADR-0005 不变）；scratch 之外：按 `writesOutsideScratch`；含 Destructive 步骤：一律审批，scratch 中也一样。
- 写系统主数据的操作（[ADR-0019](0019-master-data-writes.md)）不能成为计划的步骤，仍由各自的工具逐次审批。
- 写入暂停（ADR-0010）中的项目或实例，计划不开始。

### 3. 执行不超出批准的范围
每步执行前，Bridge 在同一次调用中重新规划。它的变更清单必须与批准的一致（预测的步骤按批准的模式匹配），修改范围不得超出批准的范围；否则在这一步之前停下，返回 `PLAN_STALE`，`metadata.conflicts` 列出不一致的对象。持久化的前置条件用定位符和内容哈希核对，从不使用运行时字符串标识（设计 4.6.2）。

### 4. 备份
- 审批之后、第一步之前，用 `CopyProject(Snapshot)` 备份一次，核对页数（ADR-0013 的方式）。只有 Write 步骤、目标在 scratch 中的计划也备份：后面的步骤失败时，前面已提交的步骤不会自动回滚，备份是整个计划唯一可靠的退路（示例项目约 0.6 秒，A18）。
- 计划中的 Destructive 步骤，在它执行之前另按 ADR-0013 备份一次（那时项目已含前面步骤的修改）。
- 备份失败就不开始（`BACKUP_FAILED`，`not_started`）；备份路径写进审计和计划结果；不自动删除。

### 5. 逐步执行
- 每步走现有的 `*.execute`：`LockingStep` → `SafetyPoint` → `UndoStep` → `QuietModeStep`，撤销步骤的描述为 `AI: plan <planId 前 8 位> <k>/<n> <操作>`，执行后读回。
- 步与步之间释放主线程，工程师的 EPLAN 保持可用；下一步开始前若 EPLAN 正忙或有模态对话框（`EPLAN_BUSY`），计划停在这里。
- **第一个失败就停下**，不继续，不自动撤销已提交的步骤。撤回由工程师在 EPLAN 中按撤销步骤逐个 Ctrl+Z，或打开备份；没有恢复工具（同 ADR-0013）。

### 6. 计划级结果
各步的 `execution` 仍是 ADR-0010 的四个值。计划级的 `execution`：

| 值 | 条件 |
|---|---|
| `not_started` | 没有任何一步开始（被拒绝、审批未通过、开始前 `PLAN_STALE`、备份失败） |
| `rolled_back` | 第一步失败并已回滚，没有其他步骤开始 |
| `committed` | 全部步骤已提交 |
| `partially_committed` | 至少一步已提交，之后某一步 `not_started` 或 `rolled_back`，计划停下 |
| `unknown` | 任何一步为 `unknown` |

- 不变式（Small 测试）：`retryable: true` 只出现在 `not_started`、`rolled_back`；`partially_committed` 从不可重试；计划为 `unknown` 当且仅当某一步的 `reason` 为 `OUTCOME_UNKNOWN`，并按 ADR-0010 暂停写入。
- 结果带 `steps[]`（序号、操作、`execution`、错误码、撤销步骤的描述）、备份位置和校验摘要。`partially_committed` 的 `message` 说明已完成和未完成的步骤，下一步是 `eplan_plan_get` 查看差异，再决定继续还是恢复。
- `partially_committed` 只出现在计划工具中；现有写工具的 `execution` 仍是四个值。

### 7. 中断与继续
- Host 只在上一步的结果确定之后才发下一步。第 k 步执行中超时或断开时，按 ADR-0010 用 `outcome.get` 取回这一步的结果，不再发后面的步骤；Host 重启后，按悬空写入的做法（`DanglingWrites`）处理计划中的步骤。计划的结果按第 6 条推出。
- **继续剩余的步骤要重新编译、重新审批**：`eplan_plan_apply(plan_id, resume: true)` 按当前状态编译剩余的步骤，得到新的计划和新的审批；批准从不复用。

### 8. 审计
新增 `plan_approval`（`planId`、`planHash`、各步变更摘要、渠道、决定）和 `plan_result`（计划级结果、各步摘要、备份、校验摘要）；各步的 `execution_started`、`execution_result` 增加 `planId` 和 `step`。哈希链不变。

## 后果
- **好的**：
  - 一个意图一次决定，工程师看到的是整体的差异；
  - 每个计划都有开始前的备份，任何失败都有退路；
  - 工程师的 EPLAN 在步与步之间可用，每步能单独撤销；
  - "做了一部分"有专门的值，不会被误读为成功或失败。
- **坏的或要付出的代价**：
  - 变更清单可能很长，要靠分组和 Workbench 的差异视图帮助工程师审阅；
  - 计划可能停在中间，需要工程师决定继续还是恢复；
  - 每个计划多一次备份的时间和磁盘空间；
  - 计划工具的结果多一个取值，客户端和评测要认识它。
- **后续行动**：
  - 实现计划工具时，ADR-0005、ADR-0010 各加一段修订说明指向本 ADR；[工具设计规范](../standards/mcp-tool-design.md) 6.2、6.3、第 8 节写明计划级结果；架构 6.3 增加计划的时序；
  - [security.md](../standards/security.md) 增加"计划文件在审批与执行之间被改""执行超出批准的范围"两条威胁及措施（编号按当时的最大值顺延）；
  - 测试：Small（结果表与不变式、绑定）；Medium（假 Bridge：一次审批、备份、第 k 步失败、步骤之间断开、Host 重启、重新规划不一致时停下）；Large（示例项目的 scratch 副本上执行多步计划、逐步 Ctrl+Z、中途失败后的备份可以打开）。

## 各方案利弊
### A1 每步审批
- 优点：每一步都单独确认。
- 缺点：一个意图多次打断工程师，容易不看就批准；步骤之间工程师可能改动项目，后面的批准针对的是变了的状态。
### A3 Destructive 步骤单独审批
- 优点：危险的步骤多一道确认。
- 缺点：计划可能在已经做了一部分之后才被拒绝；A2 已经醒目标出 Destructive 步骤，并且每个 Destructive 步骤前另有备份。
### B1 整个计划一个事务
- 优点：失败时整体回滚。
- 缺点：长时间占住主线程；有的操作不能放进 `SafetyPoint`（A13）；进程死亡时照样留下部分修改（A15）；嵌套事务的行为没有验证。
### C1 只在 Destructive 时备份
- 优点：省时间和空间。
- 缺点：Write 步骤组成的计划停在中间时，只能逐步 Ctrl+Z，进程死亡后撤销历史消失（A15），没有退路。
### D3 把部分完成归为 `unknown`
- 优点：不改变取值。
- 缺点：结果其实是确定的；`unknown` 会触发写入暂停，让工程师多做一次不必要的确认。
