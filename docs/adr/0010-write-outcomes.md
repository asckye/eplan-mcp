# ADR-0010：采用封闭的执行状态报告写操作结果，中断后向 Bridge 查询结果

| 决策人 | 项目负责人 |
| 门的类型 | 单向门：第一批写工具发布后，`execution` 字段和两个新错误码就是工具契约的一部分；Bridge 内部如何保存结果是双向门 |
| 影响 | 修订 [ADR-0005](0005-safety-model.md) 第 3、4 节：补充"结果未知"的处理和写入暂停，其余规则不变 |

## 背景与问题
ADR-0005 规定写操作在 Bridge 的事务包装中执行，失败回滚，成功提交。但结果只用文字说明（`EPLAN_OPERATION_FAILED` 写"已回滚"，见 [mcp-tool-design 6.3](../standards/mcp-tool-design.md#63-错误码表)），而且 Host 有时并不知道结果：`BridgeClient` 每次 `invoke` 最多等 30 秒，超时后断开连接，返回可重试的 `TIMEOUT`，[M1 设计](../design/2026-10-13-m1-skeleton.md) 4.5 写明这只在只读时没有问题。WPF `Dispatcher.Invoke` 的超时只限制等待开始的时间，委托开始后会执行完（WPF 文档；进入超时的情况见 [api-notes](../eplan/api-notes.md) A9）。所以 Host 报告超时后，写操作仍可能提交；模型一重试，同一个页面就建了两次。

写操作被中断有四种情况：① Host 等待超时；② 管道断开（客户端重启、Host 被结束）；③ EPLAN 在途中崩溃或被强制结束；④ 回滚本身失败。① 和 ② 中 Bridge 知道结果，③ 和 ④ 才是真正的"结果未知"。

项目负责人复查 TIA_Portal_Openness_MCP 项目后，决定借鉴它的做法：封闭的结果状态；结果未知时返回专门的错误、禁止自动重放、人核实之前停止写入。TIA 不能回滚，调用方在 TIA 进程外；本项目的 Bridge 在 EPLAN 进程内，并且有 SafetyPoint（A7），所以设计从本项目的条件出发。这件事要在 M3 第一批写工具发布之前定下（见"后果"）。

## 决策驱动因素
- 数据完整性第一（[架构](../architecture/architecture.md) 1.3）：不能因为重试把一个修改做两次；无法确定时宁可停下。
- 对代理友好：项目有没有被修改，用一个字段说清楚。
- EPLAN 主线程串行；Bridge 在进程内，知道每个写操作的结果；SafetyPoint 不提交就回滚（A7、A9）。只在真正无法确定时才需要工程师介入。

## 备选方案
括号中是不选的原因。
- **结果的表达**：A1 维持现状，只写在 `message` 中（模型要读文字推断）；A2 布尔字段 `projectChanged`（分不清"没执行"和"已回滚"，`null` 容易误读）；**A3 封闭枚举 `execution`**；A4 TIA 式的多个维度（"部分完成"在一次调用一个 SafetyPoint 的模型下不会出现，多出的维度只增加契约）。
- **中断之后**：B1 Host 一律返回"结果未知"（最常见的 ① 和 ② 也要人处理）；**B2 Bridge 在内存中保留最近写操作的结果，Host 重连后查询，查不到才返回"结果未知"**；B3 在 B2 的基础上把结果写入磁盘（EPLAN 崩溃时记录最多说明"开始了、没结束"或"已提交"，而崩溃后修改是否还在本身未经验证，仍是未知；却给每次写操作增加磁盘 I/O 和新的落盘格式）；B4 Host 用同一个请求 ID 自动重发，由 Bridge 去重（EPLAN 崩溃后去重记录随之消失，可能把修改做两次）。
- **结果未知之后**：C1 只返回错误（依赖模型自觉，换一个会话就不知道发生过什么）；C2 由 Bridge 在内存中暂停该实例的写入（结果未知的主要原因正是 EPLAN 崩溃，暂停会随进程消失）；**C3 由 Host 在数据目录中按项目记录暂停，人确认后解除**。TIA 的进程租约不需要：主线程本来串行，计划指纹已经防止交错写入。
- **协议**：**D1 新增一个操作，协议版本不变**；D2 协议版本升到 2（只增加操作时，升版本不带来额外信息）。

## 决策
建议选择 **A3 + B2 + C3 + D1**。

### 1. 执行状态 `execution`
Write、Destructive（以及启用后的 Code）级工具的结果和错误都带 `execution`，Read 级工具不带。只有四个值：

| 值 | 含义 |
|---|---|
| `not_started` | 没有开始修改：执行前被拒绝，或者是 `dry_run`、变更清单为空 |
| `rolled_back` | 开始修改，失败后已回滚，项目与调用前相同 |
| `committed` | 修改已提交 |
| `unknown` | 无法确定项目是否被修改 |

- 成功结果是 `committed`（`dry_run` 和无变化时是 `not_started`）；提交之后才出现的问题（例如撤销步骤没有正常关闭）作为成功结果中的警告返回。
- 两条不变式，由 Small 测试保证：`retryable: true` 时只能是 `not_started` 或 `rolled_back`；`execution` 为 `unknown` 当且仅当 `reason` 为 `OUTCOME_UNKNOWN`。

现有错误码的 `retryable` 不变，`execution` 按发生的阶段取值（同一个错误码可能出现在不同阶段）：

| 阶段 | 错误 | `execution` |
|---|---|---|
| 执行开始之前 | 参数、对象、策略、审批、审计、连接类错误，`PLAN_STALE`，`EPLAN_BUSY`（被放弃的调度事后不会执行，A9），`TIMEOUT`（规划阶段，或已确认执行请求没有送达） | `not_started` |
| 事务中失败 | `EPLAN_OPERATION_FAILED`、`LOCK_FAILED`、`LICENCE_*`、事务包装内捕获的 `INTERNAL` | `rolled_back` |
| Bridge 已提交，Host 随后出错 | `INTERNAL` | `committed` |
| 执行请求发出后中断且取不回结果，或回滚本身失败 | **新增** `OUTCOME_UNKNOWN`，不可重试：不要重复调用，先请工程师在 EPLAN 中检查，可以用读工具查看现状 | `unknown` |
| 项目的写入已暂停（第 3 节） | **新增** `WRITES_SUSPENDED`，不可重试 | `not_started` |

写工具发出执行请求之后，不再直接返回可重试的 `TIMEOUT`，而是先按第 2 节取回结果。

### 2. 中断后取回结果
**Bridge**：以 `invoke` 中已有的 `correlationId`（Host 每次 `invoke` 新生成的 GUID，下称请求 ID）为键记录写操作：收到时为"排队"，在主线程上开始时为"执行中"，`Commit()` 返回后立即记为 `committed`，回滚完成记为 `rolled_back`，回滚抛出异常记为 `unknown`，进入主线程前被拒绝记为 `not_started`。**先记录，再发送响应。**
- 只保存在内存中，最多 256 条，"排队"和"执行中"的不会被挤出，EPLAN 退出时消失；只记元数据（请求 ID、操作、项目、状态、错误码、时间），不含项目内容。
- 同一个请求 ID 再次到达时不再执行，直接返回已记录的结果。
- 新操作 `outcome.get {requestId}` 在管道线程上回答，不经过主线程，写操作还在执行时也能查询。查询没见过的 ID 时，同时把它登记为 `not_started`，迟到的同 ID 请求不会再执行，所以"没收到"就是"没有执行"；记录已被挤出时回答"已过期"。

**Host**：发出执行请求之前，先在审计中写一条"开始执行"记录。连接断开或等待超时后，按同一个管道名重连（管道名含进程号和随机值，能确认是同一个 Bridge），调用 `outcome.get`：
- `committed` 或 `rolled_back`：按这个结果返回，说明结果是事后取回的；
- `not_started`：Bridge 记录的拒绝原因；请求根本没有送达时，返回中断本身的错误（等待超时为 `TIMEOUT`，管道断开为 `EPLAN_NOT_CONNECTED`），都可以重试；
- "排队"或"执行中"：继续定期查询，直到该工具的执行时限（默认值由 M3 设计文档确定），到时仍未结束按结果未知处理；
- `unknown`、已过期，或者连不上原来的 Bridge（EPLAN 已退出或崩溃）：返回 `OUTCOME_UNKNOWN`，并暂停写入（第 3 节）。

**永远不自动重发写操作。** Host 自身崩溃后重启时，从审计中找出只有"开始执行"、没有结果的记录，同样查询并补记，查不到就暂停写入。客户端取消调用时，Host 同样取回最终结果写入审计。

### 3. 写入暂停与人工确认
- **范围**：目标项目（规范化后的完整路径，与判断 scratch 相同），EPLAN 重启后仍然有效；另外暂停当时那个 EPLAN 实例的全部写入，直到它退出，因为回滚失败后同一实例中的其他项目也可能受影响。读操作不受影响。scratch 项目同样暂停。
- **记录**：Host 写在数据目录 `%USERPROFILE%\EplanMcp\state\` 中（格式由设计文档确定），同时写入审计。本机所有 Host 进程在每次写操作前检查，换一个客户端或会话也绕不过去。
- **解除**：对暂停中的项目发起下一次写调用时，Host 先单独请求一次确认，渠道与审批相同（ADR-0005 第 3 节及其修订：elicitation → Workbench → EPLAN 内的对话框 → 拒绝），不与新写操作的审批合并。表单列出工具、时间、计划中的变更清单，请工程师先在 EPLAN 中核实（需要时用 Ctrl+Z 撤销"AI: <工具名>"这一步）。确认后解除并写审计；拒绝、取消、过期或没有渠道时返回 `WRITES_SUSPENDED`。因"到时仍在执行"而暂停的，Host 在下一次写入前再查询一次，得到确定结果就自动解除。
- 没有任何 MCP 工具可以解除暂停（与 SEC-02 相同）；`doctor` 和 `eplan_session_status` 显示当前的暂停。

### 4. 协议
- 新增操作 `outcome.get`，**协议版本保持 1**，与 M2 新增读操作的做法相同（[M2 设计](../design/2026-10-18-m2-read-core.md) 4.3）；Bridge 在握手结果的 `operations` 中声明它。
- Host 只向声明了 `outcome.get` 的 Bridge 发送写操作，否则返回 `BRIDGE_INCOMPATIBLE`。"同一请求 ID 不重复执行"只约束新增的写操作，不改变已有消息的含义。

## 待验证的 EPLAN 行为
以下行为没有实测。设计按最保守的方式处理（都归为 `unknown`），不依赖它们的结论；结论只影响提示文字和工程师的核对步骤。

| # | 问题 | 现有依据 |
|---|---|---|
| U1 | 管道线程在写操作途中失效（连接断开、Host 被结束）时，主线程上的委托是否照常执行到提交或回滚 | SafetyPoint 只在主线程的委托中创建和释放，管道线程只是等待；预期不受影响 |
| U2 | EPLAN 在 SafetyPoint 打开期间被强制结束：重新打开后，项目回到操作前、留下部分修改，还是损坏 | 无 |
| U3 | `Commit()` 返回后、`CloseUndo()` 之前 EPLAN 被强制结束：修改是否已落盘，撤销历史如何 | 无 |
| U4 | 委托中发生原生访问冲突时，EPLAN 在调度器中是否崩溃，SafetyPoint 是否回滚 | 在 action 中没有崩溃（A11 的 `SysMessagesCollection` 交叉使用可以稳定复现） |
| U5 | `Commit()`、`Rollback()`、`CloseUndo()` 自身抛出异常后项目的状态 | 可能无法人为触发，按 `unknown` 处理 |

建议在第一个写工具实现之前做 **spike S8（写操作中断）**（S7 已由 ADR-0009 提议）：在示例项目的 scratch 副本上，用只供 spike 使用的插件构建，测试写操作可以设定延迟和故障点（例如新建 20 页，中途停顿）。逐项执行：结束测试用的 Host 或缩短其超时（U1）；在提交前、提交后用 `taskkill /F` 结束 EPLAN（U2、U3）；触发 A11 的访问冲突（U4）。每次之后重新打开项目，比较页数和属性，查看 `EplLog.eldb` 和撤销历史，结论写入 api-notes。强制结束 EPLAN 会丢失它当时的界面状态，所以只在项目负责人同意、没有打开其他项目时进行。如果 S8 表明崩溃前已提交的修改都会保留、未提交的都会丢弃，可以另写 ADR 引入 B3，把一部分崩溃情况变成确定的结果。

## 后果
- **好的**：模型读一个字段就知道项目有没有被改；超时不再导致重复写入；大多数中断能得出确定结果；真正无法确定时，AI 的写入停下来，直到工程师核实，而且跨会话、跨重启有效；审计中每个写操作都有结果。
- **代价**：Bridge 多了状态（结果记录、去重），Host 多了恢复流程，都需要故障注入测试；数据目录多一个 `state\`（[ADR-0008](0008-data-locations-and-instance-discovery.md) 的目录列表要补充）；极少数情况下工程师要多确认一次。
- **必须在 M3 第一批写工具发布之前定下**：`execution`、两个新错误码、写操作超时后先取回结果、`outcome.get`。按[开发流程第 8 节](../process/development-workflow.md#8-版本与发布)，事后新增字段只算次版本；但写操作超时原来是"可重试"，之后改为"可能结果未知、不可重试"，改变了已有字段的含义，属于破坏性变更，按旧行为写好的提示词和评测也要返工。
- **后续行动**（接受之后）：
  - 文档：ADR-0005 加一段修订说明指向本 ADR；[mcp-tool-design](../standards/mcp-tool-design.md) 6.2、6.3（两个错误码、`execution` 一列、改写 `TIMEOUT`）、7.1、第 8 节和[工具规格模板](../templates/tool-spec.md)；[架构文档](../architecture/architecture.md) 6.3 时序图、第 7 节数据目录、8.2–8.4、8.8（"开始执行"记录、暂停记录），第 9 节增加 Q11（写入途中管道断开，报告真实结果，不重放）和 Q12（写入途中 EPLAN 被结束，返回 `OUTCOME_UNKNOWN`，下一次写入要求确认）；[安全标准](../standards/security.md)增加"结果未知后重复写入"的威胁和措施。
  - 代码与测试：Contracts 中的执行状态、两个错误码、`outcome.get` 及往返测试；Small 测试覆盖不变式和错误码对应关系，Medium 测试用假 Bridge 覆盖途中断开、延迟提交、重复请求 ID、Host 重启。
  - M3 设计文档确定记录条数、各工具的执行时限、状态文件格式、确认表单的中英文文字；spike S8。

## 项目负责人的决定（2026-10-19，均按建议）
1. 暂停范围：目标项目，加上当时那个 EPLAN 实例的全部写入（实例退出后这一部分解除）。
2. 解除渠道：只用审批渠道，不提供命令行解除命令。
3. scratch 项目同样暂停。
4. 因"到时仍在执行"而暂停的，得出确定结果后自动解除。
5. spike S8 在第一个写工具实现之前进行：只在 scratch 副本上，项目负责人在场，EPLAN 中不打开其他项目。

## 修订（2026-10-21，ADR-0011 与 spike S8）
- 第 3 节"解除"中的渠道顺序由 [ADR-0011](0011-approval-out-of-band.md) 取代：确认只经工程师独立操作的窗口（Workbench 运行时优先，否则 EPLAN 内的对话框），不用 MCP elicitation；都不可用时返回 `WRITES_SUSPENDED`。
- spike S8（api-notes A15）表明，EPLAN 在写入途中被结束时，事务中已做的修改留在项目里，撤销历史随进程消失。所以确认表单不再建议"用 Ctrl+Z 撤销"，而是说明项目中可能只有部分修改，请工程师对照变更清单检查、手工删除半成品或恢复副本（M3 设计 4.6）。B3 因此不可行。
