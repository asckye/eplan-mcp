## 背景与问题

现在 EPLAN 只能由人启动。AI 代理遇到 `EPLAN_NOT_CONNECTED` 只能请工程师去开；改了插件要重启 EPLAN 才加载，也只能靠人或 `eng/scripts` 里的开发脚本。M10 第 2 项要把这三件事做成工具：启动、关闭、重启（替换插件后重新连上）。

风险集中在关闭：EPLAN 里可能开着工程师的真实项目，可能有对话框、正在进行的写入或等待中的审批。启动则会占用一个授权，并在桌面上弹出窗口。

## 决策驱动因素

- 硬性规则 1：真实项目只能由人处理。关闭会关掉其中打开的项目，等于替人做了决定。
- 写入进行中、审批等待中关闭，结果会变成未知（ADR-0010）。
- Host 通过 HTTP 跑在虚拟机里时（ADR-0018），它和 EPLAN 不在同一台机器，无从启动。
- 关闭 EPLAN 的干净方式还没有在本机验证过；不能凭记忆假设 API 行为。

## 备选方案

1. **三个工具，关闭按打开的项目分级**：`eplan_session_start`、`eplan_session_close`、`eplan_session_restart`。打开的项目都在 scratch 根目录下时直接执行；有 scratch 之外的项目时拒绝，提示工程师自己关。
2. 同上，但 scratch 之外的项目也可以在工程师审批后关闭。
3. 只做启动，关闭和重启仍由人做。
4. 不做，维持现状。

## 决策（提议）

选方案 1。

- **启动** `eplan_session_start(variant)`：用配置里的 EPLAN 可执行文件（未配置时取已安装的受支持版本）和变体（参数优先，其次配置，例如 `Pro Panel`）启动；等插件管道出现，期间发送进度，超时 180 秒；结果与 `eplan_session_status` 相同。已有装了插件的 EPLAN 在运行时拒绝，避免同时开两个。不需要审批。
- **关闭** `eplan_session_close(process_id)`：只关本 Host 能连上的 EPLAN。先检查：没有进行中的写入、没有等待中的审批、没有被挂起的写入；打开的每个项目都在 scratch 根目录下。任一条不满足就拒绝并说明原因，什么也不做。满足时经插件请 EPLAN 正常退出，不结束进程；退出方式实现前先在 scratch 上实机验证并写进 api-notes。
- **重启** `eplan_session_restart(process_id)`：关闭的全部检查之后再启动同一个变体；用于替换插件后重新加载。
- Host 与 EPLAN 不在同一台机器时三者都返回 `CAPABILITY_MISSING`。
- 审计记录启动、关闭的进程号、变体和结果；关闭被拒绝时记录拒绝原因。

不选方案 2：审批面板里一句"关闭 EPLAN"看不出会关掉哪些真实项目、有没有没保存的编辑器内容；真实项目交给人处理，比让人批准一个看不全后果的关闭更安全。
不选方案 3：替换插件后的重启正是代理最常卡住的地方。

## 后果

- **好的**：代理遇到 EPLAN 没开可以自己开；开发时替换插件后可以自己重启；真实项目开着时，关闭被拒绝而不是被询问。
- **坏的或要付出的代价**：启动占用授权，并在工程师的桌面上弹出 EPLAN；关闭的前置检查依赖插件能如实列出打开的项目；可执行文件的查找规则要和 `doctor` 一致。
- **后续行动**：负责人确认后写三个工具的规格；在 scratch 上实机验证 EPLAN 正常退出的方式（api-notes 新条目）；Large 测试覆盖启动、带真实项目时的拒绝、只有 scratch 项目时的关闭、重启后重新连上。
