## 背景与问题
项目负责人要求"只返回计划的可选算法插件"（[M6 设计](../design/2026-10-21-m6-engineering-packs.md) 4.14），例如端子分配、布局建议、按公司规则选型。这类算法用受限的规则格式表达不了，需要真正的代码。

现状和约束：
- ADR-0005 的 Code 级"执行任意代码……默认禁用，不在任何默认 Profile 中；即使在配置中启用，每次调用仍然需要审批"。代码中 Code 级一律拒绝。
- Bridge 在 EPLAN 进程内，除 EPLAN 自带的程序集外不带第三方依赖（架构 5.1），不能加载插件。
- Host 进程能访问数据根目录、审计和 Bridge 的管道。
- 微软文档明确说 `AssemblyLoadContext` 不是安全边界，不可信的代码不能安全地加载进可信的进程。
- Windows 上不改系统设置就没有简单可用的沙箱：限制网络要防火墙规则，AppContainer 需要额外的配置。

## 决策驱动因素
- 插件不能接触 EPLAN，不能绕过审批：它的产出必须走计划的编译、校验和审批（设计 4.8、ADR-0023）。
- 插件崩溃、卡死、耗尽内存，不能影响 Host 和 EPLAN。
- 运行谁的代码由工程师决定，并且只能在配置文件中决定（SEC-02），AI 不能自己安装或启用插件。
- 安全默认值不悄悄放宽（开发流程原则 5）。

## 备选方案
1. 不提供插件。
2. 在 Host 进程内用 `AssemblyLoadContext` 加载插件。
3. **在单独的工作进程中运行插件，纯数据进、计划草稿出。**
4. 方案 3 再加系统级沙箱（AppContainer、受限令牌）。
5. 插件写成脚本（C#、Python），由 Host 解释或编译。

## 决策
选择方案 3；方案 4 作为以后的加强。

### 1. 工作进程
- 由 Host 为每次运行启动一个工作进程：同一个 `eplanmcp.exe` 的隐藏子命令 `plugin-host`，不另装程序。
- 通信只经标准输入输出：一个 JSON 请求、一个 JSON 响应；日志写 stderr，Host 转进自己的日志。
- 进程放进 Job Object：随 Job 关闭结束、内存上限（默认 1 GB）、CPU 时间和墙钟时间上限（默认 60 秒）、不允许子进程；不继承句柄；环境变量清空，只留运行所需的系统变量（不含 `EPLANMCP_*`、管道名）；工作目录是数据根目录下新建的临时目录，运行后删除。
- **做不到的**：工作进程仍以当前用户的权限运行，能读写用户能访问的文件、能联网。所以插件按 Code 级对待，启用就是信任它的代码（第 4 条）。

### 2. 输入：纯数据
快照中一个柜范围内的对象（带定位符）、生效配置的值、插件参数、格式版本。没有句柄、没有 Bridge 的连接、没有文件路径；大小有上限（默认 64 MB）。

### 3. 输出：计划草稿
- 与工作流编译用的步骤格式相同，只能用封闭的操作目录中的操作；也可以返回候选（`Candidate`），只作为候选。
- Host 按 schema 校验，检查操作、修改范围在柜内、定位符能解析，再按设计 4.8.2 编译成计划；执行照常走 ADR-0023 的审批和备份。插件从不直接执行任何东西。
- 超时、崩溃、非零退出、输出不合格式：本次运行失败，返回新的错误码 `PLUGIN_FAILED` 并说明原因（不涉及 EPLAN，不带 `execution`），计划不生成。

### 4. 级别与启用
- Code 级，默认关闭。启用只能在 `config.json` 中：`plugins.mode` 为 `off`（默认）或 `on`；`plugins.allowed` 按插件 ID、版本和插件目录的 SHA-256 列出。不在列表中或哈希不符的插件不运行；`off` 时与插件有关的参数不出现在工具 schema 中。
- **列入允许列表的插件每次运行不再单独审批**（Q1，项目负责人 2026-10-21 决定"不再单独审批"）。这是对 ADR-0005 第 1 节 Code 级"每次调用都要审批"的一处窄的放宽，只适用于插件运行，理由：
  - 允许列表本身就是工程师信任这段代码的决定，只能手工修改配置文件；
  - 运行时的审批对话框无法让工程师判断代码做了什么，安全性不因此增加；
  - 插件的产出是计划，执行前照样逐次审批。
- 没有任何 MCP 工具能安装、启用插件或修改允许列表。插件由工程师复制到 `<数据根目录>\plugins\<ID>\<版本>\`（含 `plugin.json`：ID、版本、入口程序集、契约版本），或用 CLI `eplanmcp plugin install`（不是 MCP 工具）。
- 工程包从不包含插件（ADR-0024）；包可以声明可选的插件要求（`plugin:<ID>`）。

### 5. `AssemblyLoadContext`
在工作进程中，每个插件一个加载上下文，用 `AssemblyDependencyResolver` 按插件的 `.deps.json` 解析依赖；契约程序集只从默认上下文加载一份，保证类型一致。它只解决依赖冲突，**不是安全边界**。

### 6. 审计
每次运行一条 `plugin_run` 记录：插件 ID、版本、哈希、输入和输出的摘要、耗时、结果。

## 后果
- **好的**：
  - 算法可以用真正的代码实现，又碰不到 EPLAN，绕不过审批；
  - 插件出错只影响这一次运行；
  - 运行谁的代码由工程师在配置文件中决定，可以审计。
- **坏的或要付出的代价**：
  - 启用的插件能以用户权限读写文件、联网，这一点只能靠工程师的信任决定；
  - 每次运行要启动进程、序列化数据，比进程内慢；
  - 多一套契约（输入、输出、`plugin.json`）要维护版本。
- **后续行动**：
  - 第 5 阶段实现，之前不开工；
  - [security.md](../standards/security.md) 增加"插件代码"威胁及措施（编号按当时的最大值顺延）；
  - 工具设计规范第 8 节的级别表下注明本 ADR 的例外：**已完成**（2026-10-21，与接受本 ADR 同一个 PR）；
  - `doctor` 显示 `plugins.mode` 和允许列表的核对结果；
  - 测试：Small（允许列表与哈希、输出校验）；Medium（超时被结束、内存超限、崩溃、输出越出柜的范围被拒绝、工作进程拿不到管道名和数据目录的环境变量）；
  - 方案 4 的系统级沙箱在有需求时另做 spike。

## 各方案利弊
### 方案 1：不提供插件
- 优点：没有新的风险。
- 缺点：不满足负责人的要求；复杂算法只能塞进规则格式或由模型临场发挥。
### 方案 2：Host 进程内
- 优点：快，部署简单。
- 缺点：插件能访问 Host 的一切（管道、审计、配置），崩溃会带倒 Host；微软文档明确说加载上下文不是安全边界。
### 方案 4：系统级沙箱
- 优点：能限制文件和网络访问。
- 缺点：需要额外的系统配置，可能触碰"不修改系统设置"的约束；先用方案 3，有需求再加。
### 方案 5：脚本
- 优点：写起来方便。
- 缺点：仍是执行任意代码，还要带解释器或编译器；与 ADR-0021 否决经脚本执行的理由相同。
