## 背景与问题

`full` 现在有 128 个工具。客户端在每次会话开头读入全部工具定义，工具多了会占上下文，有的客户端还限制工具数量；`core` 只有 25 个，又缺了画图和主数据工具。M10 第 4 项要的是第三种用法：模型先**搜索**工具，再**查用法**，再**调用**，会话开头只看到几个工具。

搜索和查用法没有问题：`eplan_tool_usage` 已经存在，加一个按意图搜工具的只读工具即可。难点在"调用"：要在只暴露几个工具的前提下调用其余工具，就要有一个按名字转发的分发工具。而客户端的权限提示（例如"允许只读工具，写入工具每次问我"）是按**工具名和它的 MCP 注解**做的。一个分发工具只有一组注解，客户端就分不清这次转发的是只读查询还是删除页面。

服务端的安全机制本身不受影响：转发进来的调用走的是同一个工具方法，scratch 判断、`WritePipeline` 的审批、备份、审计、预览默认值都照旧。受影响的只是客户端这一层。

## 决策驱动因素

- 风险等级由可信的一侧计算（手册 UI-16），不能取自调用方声明。
- 客户端那一层的"只读放行、写入询问"必须保留，否则用户在客户端里设的权限就形同虚设。
- 不改 `full` 和 `core`，已经在用的客户端不受影响。
- 分发不能成为绕开 Profile 的后门：转发的目标必须是本 Profile 声明可以转发的工具。

## 备选方案

1. **两个分发工具，按目标工具的安全级别分开**：`eplan_tool_read`（`readOnlyHint` = true）只转发只读工具；`eplan_tool_write`（`destructiveHint` = true）只转发写入和破坏性工具。目标是哪一级，由服务端按目标工具自己的注解判定，传错了直接拒绝。
2. **一个分发工具**，注解取最坏情况（破坏性）。客户端对每次调用都要询问，包括只读查询。
3. **不做分发**：discovery 只给搜索和用法，再加 `core` 的 25 个工具；其余工具要用户换到 `full`。
4. **不做这个 Profile**，交给客户端自己的工具延迟加载。

## 决策

选方案 1。

- 新增 Profile `discovery`，只注册四个工具：`eplan_tool_search`（新，只读：按关键词或意图搜工具名、标题、描述和用法，离线）、`eplan_tool_usage`（已有）、`eplan_tool_read`、`eplan_tool_write`。
- `eplan_tool_read(tool, arguments)`：目标工具必须已注册且 `readOnlyHint` 为 true，否则 `INVALID_ARGUMENT`，并在提示里说用哪个分发工具。
- `eplan_tool_write(tool, arguments)`：目标工具必须已注册且 `readOnlyHint` 为 false；`dry_run` 的默认值、审批、scratch 规则都由目标工具自己决定，分发工具不加也不减。
- 参数按目标工具的输入 schema 校验，错误与直接调用目标工具时完全相同；结果原样返回，审计记录同时写分发工具名和目标工具名。
- 两个分发工具不能互相转发，也不能转发 `eplan_tool_search` 和 `eplan_tool_usage`。
- `full` 和 `core` 不注册分发工具。

不选方案 2：只读查询占调用的大多数，每次都弹询问，用户很快会改成"全部允许"，等于把写入的询问也放掉了。
不选方案 3：画图和主数据工具恰恰不在 `core` 里，discovery 就失去意义。
不选方案 4：各客户端的延迟加载能力差别很大，本项目控制不了。

## 后果

- **好的**：会话开头只读入 4 个工具定义；客户端仍能按"读/写"两级设权限；服务端安全面不变。
- **坏的或要付出的代价**：客户端看不到目标工具的名字，权限只能到"读/写"两级，不能到单个工具；模型多一步搜索；目标工具的输出 schema 不再出现在工具列表里，只能经 `eplan_tool_usage` 查看。
- **后续行动**：负责人确认后写 `eplan_tool_search`、`eplan_tool_read`、`eplan_tool_write` 的工具规格；契约快照为 `discovery` 单独存一份；评测里加一组只给 discovery 的任务，比较参数重试次数。
