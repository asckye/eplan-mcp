# Spike S31：快照提取的完整性、确定性与修改标记

> 状态：**完成**（2026-10-21，r1–r3）。M6 设计 4.6 的 spike（规范快照）。提取只读；`reopen`、`marker` 只在 scratch 副本上进行。

## 问题
1. 读出一个项目的全部内容（每个对象的全部已有属性）要多久、多少内存；
2. 项目不变时，两次提取的内容是否逐字节相同；关闭再打开之后呢；
3. 提取会不会改写项目文件（A17 中导出会改写 `User.eod`）；
4. 位置的精度；
5. 有没有可靠的修改标记，能指出改了哪一页。

## 方法
- `SpikeS31Action` 在主线程上经调度器运行（`LockingStep` + `QuietModeStep`）。
- 快照按页组织：页的全部已有属性；页上的每个放置对象（`page.AllPlacements`）按类型名和 `ObjectIdentifier` 排序，记下类型、编号；功能另记位置和全部已有属性（`Function.Properties.ExistingIds/ExistingValues`）；连接（`DMObjectsFinder.GetConnections`，按 `Connection.Page` 归页）记两端的编号和全部已有属性；占位符记名称和值集。每页的规范文本算 SHA-256。
- **light**（r2）：页的属性照旧，功能只记全名，连接只记两端。
- `extract`：连续两次快照并比较，前后对项目 `.edb` 中的文件（不含 `.lck`）算哈希；`reopen`：两次快照之间关闭再打开项目；`marker`：读项目和每页的修改日期，改一页的描述（提交），再读一次并比较快照。
- 项目：夹具和写副本（EPLAN 示例项目的副本，321 页）。环境：EPLAN 2026.0.3.25421，Electric P8。

## 结果
**完整快照**（每个页、功能、连接的全部已有属性）：

| | r1（未释放） | r3（逐个释放） |
|---|---|---|
| 耗时 | 463 秒、479 秒 | 586 秒（一次） |
| 属性值 | 5,143,410 | 同 |
| 文本 | 150 MB，518 万行 | 同 |
| 最慢的一页 | 54–56 秒 | 50 秒 |
| EPLAN 工作集 | 937 MB → 1,805 MB（第一次后），第二次后 EPLAN 内存耗尽退出 | 1,406 MB → 2,154 MB（含插件持有的 150 MB 文本），调用结束后回到 1,476 MB |

🔴 r1 没有释放 `AnyPropertyId` 和 `PropertyValue`（都是 `IDisposable`）。第二次快照结束、报告写出后 11 秒内，EPLAN 记下一条 ErrorLevel 5 的错误（文字乱码，看起来是"硬件错误：存储空间不足"），随后关闭（"Application closed"）。

**light 快照**：4.6–6.2 秒；154,401 个页属性值，3,920 个功能、1,302 个连接、2 个占位符，共 36,134 个放置对象；5 MB；每页平均 14–19 ms，最慢 35–63 ms；工作集增加约 87 MB。

**确定性**：
- 同一次打开中连续两次快照：321 页的哈希全部相同（完整和 light 都是）。
- 关闭再打开之后：**321 页全部不同**。第一处差异是属性 2000：`53/4/21/0` → `89/4/21/0`。这个属性的值是运行时字符串标识，其中的数据库号每次打开都变（A32、A34）。
- 提取前后项目 `.edb` 中的文件（不含 `.lck`）没有变化：只读提取不改写 `User.eod`。

**位置**：7,840 个坐标中 7,651 个是整毫米，98 个在 0.1 mm 上，4 个在 0.001 mm 上，87 个更细（如 `159.179375`、`93.103115046302008`）。

**修改标记**（改 `=GAA+A1&EFS1/1` 的描述并提交）：
- 变化的有：项目的 `PROJ_LASTMODIFICATIONDATE`（Unix 秒数）和 `PROJ_LASTMODIFICATIONTIME`，以及这一页的 `PAGE_LASTAUTOMODIFICATIONDATE`/`TIME`；其他页的日期都不变；`PAGE_LASTMANUMODIFICATIONDATE` 也没有变。
- 快照中只有这一页的哈希变了（320 页相同）。
- 这一页的属性 3010（`PROPUSER_LAST_USERCODE`）同时被改写（本例中由 `EPL` 变为空）：快照中有最后修改人的用户代码、姓名、邮件、电话（3010–3013）这类个人数据。

## 结论
1. **完整读取所有属性不可行**：示例规模也要约 8 分钟、150 MB；必须按登记的属性集读取，或按页、按需读取。light 快照（几秒）说明按选定属性读取可以在一次调用中完成。
2. **必须释放属性对象**：`ExistingIds`、`ExistingValues` 和属性访问器返回的 `AnyPropertyId`、`PropertyValue` 都要 `Dispose`，否则大批读取会耗尽 EPLAN 的内存，导致它退出。Bridge 中批量读属性的代码要遵守这一点。
3. **快照的规范化**：
   - 值是运行时字符串标识（`库号/类型/编号/索引`）的属性要去掉库号，或换成定位符，否则每次打开内容都变；
   - `PROPUSER_*`（3010–3013 等最后修改人信息）属于个人数据，从快照中排除（安全规范，CLAUDE.md 第 4 条），同时它们会随修改变化，也不适合作为内容；
   - 坐标按 0.001 mm 取整再比较，核对容差至少 0.001 mm。
4. **按页的修改标记可用**：`PAGE_LASTAUTOMODIFICATIONDATE/TIME`（精确到秒）和 `PROJ_LASTMODIFICATIONDATE/TIME` 随修改变化，可以先用它们找出变化的页，再只对这些页重新提取；最终仍以内容哈希为准（同一秒内的多次修改、自动修改的范围没有验证）。
5. 只读提取不改写项目文件。

## 局限
- 只验证了改页描述这一种修改；插入、删除、移动对象、改功能属性时页日期是否变化，没有逐项验证。
- light 快照只覆盖了少数属性；"登记的属性集"的耗时要等第 1 阶段确定属性集后再测。
- 端子、电缆芯线、PLC 地址只作为功能的属性出现在完整快照中，没有单独核对。
- 只测了示例项目的规模（321 页）。
