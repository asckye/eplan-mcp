# EPLAN API 能力目录

EPLAN 官方公开 API 的成员一级清单。口径、状态、字段和阶段计划见 [API 能力覆盖设计](../docs/design/2026-10-21-api-capability-coverage.md)。

| 路径 | 内容 |
|---|---|
| `schema/catalog.schema.json` | 下面每种文件的 JSON Schema |
| `eplan-<版本>/` | 目录生成器的输出，**不要手工修改** |
| `eplan-<版本>/summary.json` | 按层次、命名空间、种类、对象类型的计数 |
| `eplan-<版本>/types.jsonl`、`members/*.jsonl` | 每个公开类型、成员一行，以 XML 文档注释 ID 为键 |
| `eplan-<版本>/data-dictionary.jsonl` | 每个属性 ID 一行 |

状态、证据和人工排除不放在生成目录中，按 ID 关联，由映射与覆盖报告维护。

## 重新生成
需要装有该版本 EPLAN 的机器。生成器只读 EPLAN 的 `Bin` 目录，不加载、不执行其中的程序集：

```powershell
dotnet run --project eng\catalog\EplanMcp.Catalog -- extract --sdk "<EPLAN 安装目录>\Bin" --out catalog\eplan-<版本>
```

同一份 SDK 两次生成的结果逐字节相同。换 EPLAN 版本时新建目录，提交前审阅差异；`assemblies.json` 记下了程序集的版本。

## 映射与覆盖报告
目录说明"有哪些能力"，映射说明"本项目用到了哪些、证据是什么"。工具在 `eng/coverage`，文件都按 ID 关联到目录：

| 路径 | 内容 | 怎么得到 |
|---|---|---|
| `mapping/bridge-usage.json` | Bridge 用到的每个 EPLAN 成员（文档注释 ID）和 action（`A:` ID），以及使用点和到达它的 Bridge 操作 | `scan`，需要装有 EPLAN 的机器 |
| `mapping/overlay.yaml` | 代码推导不出来的事实：实机记录、人工排除、环境阻断、可用性，每条写明出处 | 人工维护 |
| `mapping/tools.json` | 每个 MCP 工具 → Bridge 操作 → EPLAN API，附规格、测试、api-notes 引用和实机记录 | `generate` |
| `coverage.json`、`../docs/eplan/coverage-report.md` | 按层次、命名空间、对象类型、工具的覆盖统计，口径见设计文档第 3、4 节 | `generate` |

```powershell
dotnet run --project eng\coverage -- scan       # 扫描 Bridge，结束后自动运行 generate
dotnet run --project eng\coverage -- generate   # 由提交的文件重新生成其余三个文件，不需要 EPLAN
dotnet run --project eng\coverage -- check      # 与 CI 相同的检查
```

- **`scan`** 用插件自己的 Release 构建参数建一个 Roslyn 编译，读 EPLAN `Bin` 目录中的程序集作为引用，不启动、不连接 EPLAN。EPLAN 不在默认目录时加 `--eplan-bin <Bin 目录>`。结果记下扫描日期、最后一次改动所扫源码的提交，以及源码的 token 哈希（不含注释和空白）。
- **生成的代码不算实现**：从目录生成的内部构件（文件名以 `.g.cs` 结尾）只在有 Bridge 操作到达时计入覆盖；只有生成代码用到、没有操作到达的 ID 列在 `tools.json` 的 `unreachedGenerated` 中，不进入 `coverage.json` 的任何一级（设计文档第 8 节）。手写的代码没有操作到达时仍算基础设施。
- **两种过期，处理不同**（CI 的 "Coverage files" 步骤运行 `check`）：
  - **扫描过期只警告，不让 CI 失败**：`src/EplanMcp.Bridge.Eplan`、`src/EplanMcp.Bridge.Core` 或 `OperationNames` 在扫描之后改了代码（只改注释和格式不算）。CI 和大多数代理没有 EPLAN，没法重新扫描；所以 CI 只给出警告。但覆盖报告顶部要写明扫描已过期，以及扫描的日期和提交，所以改了 Bridge 代码的 PR 仍要运行 `generate`，把这条提示写进报告。之后有人在装有 EPLAN 的机器上运行 `scan` 并提交，提示随之消失。
  - **生成的文件与输入不一致会让 CI 失败**：工具、规格、测试、api-notes、overlay、目录或扫描结果变了，而 `tools.json`、`coverage.json`、覆盖报告没有跟着重新生成。运行 `generate`（不需要 EPLAN）后提交这三个文件。CI 的错误消息中给出同样的命令。

## 通用属性字典资源

`generate/check` 同时维护 `src/EplanMcp.Host/Tools/ApiIndex.g.base64`：已提交的操作层目录、对象字典、覆盖状态与工具证据构成确定性 JSON，经 gzip/base64 压缩后嵌入 Host。发布 ZIP 离线可用，不读取 SDK。目录未保存的摘要返回 null；该资源不计入 API 实现覆盖。用 `eplan_api_search` 发现、`eplan_api_get` 分页读取完整签名和证据。

`generate/check` 同时生成并核对 `src/EplanMcp.Contracts/Generated/PropertyDictionary.g.tsv`，源为
`eplan-2026.0.3/data-dictionary.jsonl`，不修改源目录。资源嵌入 Contracts，Host 与 Bridge 共用同一份发布数据，
运行时不依赖目录文件，也不新增 JSON 运行时依赖。TSV 保留对象类型、正式名称、可空数值 ID、obsolete 和读取分类。
`PropertyCatalog` 只做精确类型/ID/名称查询；无公开数值 ID 的名称不能转换为属性请求。
读取前须调用 `ReadRefusal`；全部 `PROPUSER_*`、2000、路径、联系人、凭据/授权类按生成器规则排除，过时属性和无公开数值 ID
的名称也不可读；本目录版本中其余公开属性为 `readable`（属性工具设计 4.3/5）。目录中没有的属性（如新版本新增）一律为
`unreviewed` 并拒绝，换目录版本须重新审查分类。`readable` 仍须通过运行时 internal/许可/副作用等检查，不授予写权限。
`PropertyAddressValidation` 校验构造 DTO 之前的 snake_case 工具 JSON，汇总 RFC 6901 路径；locator 的项目参数须为已解析路径。
值内容脱敏、运行时元数据校验和读适配器由后续 PR 实现；这里不将目录资源计为已实现或实机验证。

## 内部包装的生成
设计文档第 8 节的"最小生成器"：从目录生成任务工具内部用的构件，**不生成 MCP 工具**，运行时不做反射调用。

| 输入 | 输出 |
|---|---|
| `wrappers.yaml` 的 `types`：一个类型的 `properties` | `src/EplanMcp.Contracts/Generated/<类型>Properties.g.cs`（返回值的 DTO）和 `<类型>Api.Read`（属性读取的样板代码）；只收字符串、布尔、数值、枚举（取名称）和 `StringCollection` |
| `types` 的 `overloads`：方法组的简单名称 | `src/EplanMcp.Bridge.Eplan/Adapters/Generated/<类型>Api.g.cs` 中的重载表：签名简单的重载各一个类型化的方法，其余（目录排除的、按引用传参的、泛型的）写明不生成的原因 |
| `actions`：action 目录中的一行和类名 | `Adapters/Generated/<类名>.g.cs`：参数类（参数名和必填标记取自目录），`TYPE` 和 action 名是常量，由调用方自己写进 `ActionCallingContext`，覆盖扫描才认得出这一行 |

- **选择文件要短**：只列出某个工具要用的项，生成的代码才看得过来。不能直接生成的（索引属性、继承来的属性、返回目录中的类的属性）生成器报错，改为手写。
- `generate` 先写这些文件，再写映射和报告；同样的输入逐字节相同（LF，没有时间戳）。`check`（CI 的 "Coverage files" 步骤）发现生成的文件与 `wrappers.yaml` 和目录不一致、或者已经不再被选中时失败，消息中给出 `generate` 命令；`generate` 会删除不再被选中的文件。
- 生成的文件以 `<auto-generated>` 开头，文件名以 `.g.cs` 结尾，不手工修改；`dotnet format` 和分析器跳过它们。
- **生成的代码不算实现**：只有生成代码用到、没有 Bridge 操作到达的 ID 不计入覆盖（见上文），所以选中一个类型不会让覆盖率上升；工具用上它、扫描看到操作到达之后才算。
